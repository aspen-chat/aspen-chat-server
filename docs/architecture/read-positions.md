# Read positions

How far each user has read each channel is a row of `read_state` (`app::read_state`): the user, the channel (both cascading on delete), and a message id. The id is a position, not a reference: message ids are UUIDv7 and ordered by time, so "read up to this id" stays exact after that message is deleted, and deleting a message never writes here. A position only moves forward (`PUT /channels/{channel}/read-states/@me` with `lastRead`, answered `204`; an older report is ignored), each move is published to the user's own subject as the custom `channelRead` event so their other devices follow, and posting a message or a poll moves the poster's position to it in the same transaction. Nothing from before a member joined is unread to them: `community_user.joined_at` (and `dm_recipient.joined_at` for DMs) stands in for the position until they have read past it. A channel is unread while it holds a message by someone else after the position; the reader's own messages, and those of anyone they blocked, never make it unread. `ReadState.mentions` counts the unread messages that tag the reader (see Tagging). The `ReadState` record carries `lastRead` and `lastMessage` (the newest message by anyone else), computed in one query for every channel asked about; community reads and the DM list sideload them with `include=readStates`, and `GET /channels/{channel}/read-states/@me` reads one, answered as not found for a channel the caller may not view, as community reads leave such channels out. A thread keeps a position too, moved by reading it and by posting in it, and read only when asked for by name (`GET /channels/{thread}/read-states/@me`, or a message read's `include=readStates`); community and DM reads leave threads out. Until its reader has one there, it is the moment they joined where its parent belongs.
