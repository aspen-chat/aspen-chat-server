# Email

Email is optional, twice over. A deployment sends mail only when `[email]` is in `aspen.toml` (`app::email::Mailer`, made once per API server, `GlobalServerContext::mailer`); without it, accounts have no address, `GET /deployment` says `email.available: false`, and the deployment settings that need mail cannot be turned on (`emailSettingNeedsMail`, checked in `app::deployment_settings::update` from the dashboard and the terminal alike). And an account need not have an address unless the deployment's administrators set `email_required`.

Mail is sent by `lettre` over SMTP, written from one template (`server/templates/email/letter.html` and `letter.txt`, compiled by `askama`, which escapes the HTML version) as both HTML and plain text, in the language the account last used (`user_email.locale`, the request's negotiated locale when the address or its preferences were last written).

## Addresses

An account of this deployment holds at most one address, a row of `user_email` keyed by the user: the address, when it was verified, and what the account receives there. Addresses are checked by `app::email::parse_address` (trimmed, at most 254 characters, a mailbox `lettre` accepts) and are not unique: two accounts may share one, and nothing tells anyone whether an address is in use, which a unique index would at registration. Bots, the system account, and users of other deployments have none (`Caller::ensure_person`): their mail is their home's to send.

An address is given at registration (`email` in `POST /users`, with `newsletter` to subscribe, which only counts where the deployment has a newsletter), or later with `PUT /users/{user}/email/address`, and taken away with `DELETE` there, refused with `forbidden` while `email_required` is on. Giving, changing, or removing an address is a change to security settings, since a verified address can reset the password, so it needs a sign-in verified within `[auth] reverify_seconds` (`reauthenticationRequired`), except at registration. A new address starts unverified, with new unsubscribe links, and the address it replaced is told, when it was verified (`addressChanged`, naming the new address masked). Removing an address deletes the mail waiting to go to it.

### Verification

Every address given is mailed a six-digit code, which `POST /users/{user}/email/verification` takes; `POST /users/{user}/email/verification-codes` sends a new one, replacing the last. A code lasts an hour and is kept in Valkey as a SHA-256 digest beside the address it verifies (`email:verify:{user}`), so a code for an address the account has since changed verifies nothing; five wrong codes end it (`tooManyAttempts`), and a new one must be sent. Only a verified address receives anything but its code.

With `email_verification_required` on, a session of an account whose address is unverified (`Caller::email_unverified`, read in the same query that resolves the session token, `two_factor::EMAIL_UNVERIFIED_SQL`) is held as a session owing a second factor is: `SessionUser` refuses it with `emailVerificationRequired`, and only the email endpoints, which take `EnrollingSessionUser`, signing out, and reauthenticating reach it; its event stream is refused at `identify`, and an open one closes with 4428 when the setting is turned on (each server's open streams follow its copy of the settings) or when the account changes to an unverified address while it is on (each `emailAccountChanged` of its user says whether the account now holds an unverified address, `FeedEvent::email_unverified`). An account without an address is not held, so the setting binds an account once it gives one; `email_required` binds registration alone, and accounts made before it was turned on are not asked for an address.

### Preferences

`GET /users/{user}/email` reads the address and what it receives, and `PATCH` there changes `shown`, `newsletter` (refused where the deployment has no newsletter), `digest`, `digestTimeZone` (an IANA name `chrono-tz` knows), and `digestHour` (0 to 23), with merge-patch semantics. Each change is announced to the user's own subject as `emailAccountChanged`, naming only the user and whether the account now holds an unverified address, on which their other devices read it again.

### The shown address

An account may show its address on its profile: `user.public_email` holds the address exactly while it is verified and `shown`, so every read of a user carries it without a join, as `User.publicEmail`. `app::email::set_public_email` writes it, inside the transaction that changes either, and publishes a `user` update with `publicEmail` when it changes. A foreign user's profile carries the address their home shows (`Profile.public_email` in the sign-in assertion, read and written as the rest of the profile is at each sign-in; see Federation).

## Password reset

A forgotten password is reset by email from the sign-in screen (`app::email::reset`), in three unauthenticated steps:

1. `POST /auth/password-resets` with a username (any case, as sign-in reads it) starts a reset and answers its `id` and the account's verified address masked (`app::email::mask`): the first three characters before the `@` (fewer when it is shorter, so one is always hidden), each other one an asterisk, and the domain whole. An unknown username, an account without a verified address, a bot, or a deployment that sends no mail answers `passwordResetUnavailable` with the reason. The reset lives in Valkey for half an hour under the digest of its id.
2. `POST /auth/password-resets/{reset}/codes` with the whole address, compared without case, mails an eight-digit code when it matches (`emailMismatch` when it does not; five mismatches end the reset). Asking again sends a new code, replacing the last. One account is mailed at most five reset codes an hour, however many resets ask, so nobody can fill an inbox by starting resets from many addresses.
3. `POST /auth/password-resets/{reset}/completion` with the code and a new password replaces the password, ends every sign-in of the account (`app::login::revoke_all_sessions`, which closes their event streams), and tells the address (`passwordWasReset`). Five wrong codes end the reset. Its second factors stay, so signing in still asks for one.

What step 1 shows confirms that a username exists, which registration's `usernameTaken` does already; the address itself stays behind its mask. Each step is limited per address in the `sign_in` group, and the second and third per reset too.

## The outbox

Nothing is sent while a request waits. Whatever causes mail writes a row of `email_outbox` in its own transaction (`outbox::queue`): the account, the address when the mail names one (a code for the address it verifies, a notice to the address an account left) or none for the account's verified address as it is when sent, a priority, and the mail as JSON (`outbox::Mail`). So mail goes exactly when what caused it commits, and survives a restart.

The servers whose `[email]` has `send` on (the default) send from the table (`outbox::spawn_sender`); those with it off only queue, and need no SMTP credentials, so a large deployment can keep the credentials and the work of sending and making digests on servers chosen for it, while a small one sends from every server. A sender claims a batch by pushing each row's `not_before` five minutes on under `FOR UPDATE SKIP LOCKED`, so servers sending at once never claim one row twice and a server that dies mid-batch leaves its rows to be claimed again, and sends them eight at a time. It takes the highest priority first: a password reset (someone is waiting at the sign-in screen), then a verification code, then notices, a newsletter test, digests, and newsletters, however many of those wait. A server that queues mail someone waits for (a reset, a code, a newsletter test or send) publishes on the plain NATS subject `aspen.email.wake` once it commits (`app::email::wake`), which wakes every sender at once, whichever server queued it; otherwise each looks every five seconds, so a wake-up lost costs only that. Where `[email] max_per_second` is set, every sender takes each piece from one GCRA bucket in Valkey (`email:send-rate`, `app::rate_limit::take`, the script the API's limits use) before handing it to the SMTP server, so the deployment keeps to its provider's quota however many servers send (a second's worth may go back to back), and claims no more than a second's worth at a time, so a reset queued behind a burst waits about a second per sending server; a Valkey failure lets mail through unthrottled, as the API's limits do, and is logged. Each row is checked as it is sent (`outbox::recipient`): nothing goes to a deleted account, a digest or newsletter goes only to an account still verified and still subscribed, and a code goes only to the address the account still holds. A row sent is deleted; one the SMTP server refuses for good is deleted and logged; one it cannot take now waits a minute, doubling each time, for eleven attempts, about a day. `aspen_emails_sent_total` and `aspen_emails_failed_total` count them.

## The daily digest

An account that turns on `digest` at a verified address receives, once a day at `digestHour` o'clock in `digestTimeZone`, mail telling it what arrived for it since the digest before (`app::email::digest`). `user_email.digest_next_at` is when the next is due (`digest::next_due`: the next time that hour comes there, the hour after when a clock change skips it, at a fixed point of the hour drawn from the account's id, `digest::spread`, so everyone who chose 8:00 in one zone is spread over the hour rather than due at once), and `digest_since` where it starts, set when the digest is turned on, so the first covers only what arrived after.

Every sending server looks each minute for digests that are due, claiming twenty at a time under `FOR UPDATE SKIP LOCKED`, so each is made once. A digest covers the channels the account may view in its communities (`Visibility`, as it stands when the digest is made) and its DMs and group DMs, never threads, and leaves out what never makes a channel unread (`app::read_state`): the account's own messages, those of anyone it blocked, and those at or before its read position, as well as channels and DMs it has muted. Of what is left it tells of the five earliest messages of each of the twenty places where something arrived most recently, as plain text cut to 300 characters with tags and custom emoji by name (`Names::excerpt`), and how many more each holds, linking to each place in the web client (`[web_client] url`) or by an `aspen://app/…` link where none is set; and how many more places hold something. A digest with nothing in it is not sent, and a banned account's is skipped. Either way the next is scheduled and `digest_since` moves on.

## The newsletter

Where the deployment setting `newsletter_enabled` is on, accounts may subscribe at registration (the box starts unticked) and in their settings, and holders of Send newsletters (`DeploymentPermission::SendNewsletters`, bit 14, which the migration gave every role holding Manage deployment settings) write posts at `/admin/newsletter/posts` (`app::email::newsletter`). A post is Markdown, sent as HTML made by `pulldown-cmark` (`newsletter::html`, which shows HTML written into the Markdown as text and drops links that are not `http`, `https`, or `mailto`) and as the Markdown itself. A draft may be edited, deleted, previewed (the record carries its `html`), and sent as a test to its sender's verified address (`POST …/test`). Sending (`POST …/sending`) fixes it and marks it sent; the senders then queue its mail a thousand subscribers at a time in order of their ids (`newsletter::queue_some`, `queued_through`, `recipients`), so a newsletter to a million subscribers is never one transaction. Sent posts stay, as the archive.

## Unsubscribing

Each digest and newsletter carries `List-Unsubscribe` and `List-Unsubscribe-Post: List-Unsubscribe=One-Click` (RFC 8058) and a link at its foot, all to `/email/unsubscribe?list={newsletter|digest}&token={token}` on `[email] public_url` (`https://` and the federation domain when unset). The token is random per address (`user_email.unsubscribe_token`), replaced when the address changes. A `GET` there, which mail scanners follow, shows a page asking to confirm (`api::email::unsubscribe_page`); a `POST`, the page's button or a mail program's one-click unsubscribe, unsubscribes and says so. Both are served outside `/api/v1` and limited like the API.

## Deleting an account

Retiring an account (`app::user::retire`) deletes its address, its waiting mail, and its shown address with it.

## When access is given or taken away

1. **Who can observe it, and by which routes?** The address and preferences: the account alone, through `GET /users/{user}/email` and `emailAccountChanged` (its own subject). The shown address: whoever reads the user (`User.publicEmail` in REST reads and sideloads, `user` updates to everyone who shares a community with them, `UserEverywhere`), and other deployments the user signs in to. A digest: the account's own verified address, telling of channels it may view. The newsletter archive: holders of Send newsletters.
2. **What decides it, and where is that checked?** The address is the user themself's (`api::email::own`); the shown address is `shown` and `verified_at` together, written to `user.public_email` by `set_public_email`; a digest's channels are decided by `Visibility::load` and membership in the digest's SQL, when it is made; the newsletter endpoints by `DeploymentAccess::require(SendNewsletters)`.
3. **When it is lost, what happens to what is already open?** Hiding the address, changing it, or removing it clears `public_email` and announces it in the same transaction, so every open stream drops it; clients replace the user's record. Losing view of a channel removes it from the next digest; a digest already made is a snapshot, and one queued in the minute before is sent as it was. Removing the address deletes the mail queued for it. A ban skips digests and newsletters from then on; a deleted account's mail is deleted with it. A sign-out or password change does not stop mail: it goes to the address the account verified. Losing Send newsletters refuses the next request; a post already sent finishes going out.
4. **When it is gained, how does a client already open find out?** The `user` update with `publicEmail` reaches everyone who shares a community; `emailAccountChanged` tells the account's other devices to read their settings again.
5. **Does every path that changes it announce it?** Setting, removing, verifying, and the preferences publish inside their transactions; the terminal changes no addresses; account deletion publishes the user's deletion. Unsubscribing by link announces `emailAccountChanged`.
6. **Is it published inside the transaction that makes the change?** Yes; nothing here concerns a community, so a rollback needs no `communityResync`.

`scripts/check_permissions.py` checks the shown address appearing and disappearing for another member over REST and the event stream, and a digest leaving out a channel the reader lost view of.
