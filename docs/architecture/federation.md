# Federation

A user of one deployment may use others: their home deployment is where the account was made, any other is foreign to them, and they are a foreign user there. Five phases build it: (1) each deployment's identity, key, policy, and directory of other deployments; (2) signing in abroad, with foreign users as local rows naming their home; (3) a client holding sessions on several deployments; (4) DMs across deployments and the notices between them; (5) revocation, deletion notices, and moderating foreign users. All five are built (`app::federation`, `api::federation`, and in the client `Deployments`; see `client/docs/architecture/deployments.md`).

A deployment is its domain (`app::federation::Domain`: a DNS name of two or more labels, lowercase, with `:port` when not 443, never an IP address), the host of its `public_url` when that is `https` (a deployment at an `http` address has none and takes no part), and an Ed25519 key pair (`federation_key`, the current one being the one not retired, made by the first server to start with a domain, with `ring`, which also signs and verifies). The private key is kept in the database so that every API server signs with the same one, which makes the database's backups as sensitive as the key. It publishes its domain, keys, and gates at `GET /.well-known/aspen` (`DeploymentDocument`: the current key first, then those it replaced within `HANDOVER_WINDOW_DAYS`, ninety), outside `/api/v1`, unauthenticated, cacheable for five minutes, and `404` without a domain. Federation needs HTTPS: other deployments are reached only at `https://{domain}`.

Policy is gates, which are deployment settings (`FederationPolicy`, read from each server's copy of the settings; see Administration): for users and, separately, bots, `emigration` (this deployment's accounts using others) and `immigration` (others' accounts using this one), each `closed` (the default), `open`, `allowList`, or `blockList`. The modes operators speak of are the users' gates: none, emigration, immigration, and full, each open or with a list. A gate with a list reads one of twelve lists (`FederationList`, named by who, which way, and allow or block: `usersEmigrationAllow` … `botsSharedBlock`); with `shared_list` both directions read the `Shared` list, and must then be the same kind. Every list keeps its entries whether or not a gate reads it, so switching a gate from an allow list to a block list never turns the allowed into the blocked. `admits` decides from the gates and the lists a deployment is on, and each directory record carries the result as `admission`. Holders of Manage federation change the gates from the dashboard (`PATCH /admin/federation`) and the terminal from `settings set`; every server follows at once, a gate opens only once the deployment has a domain, and a change to an immigration gate or its shared list signs out at once the users of other deployments it no longer admits (`standing::shut_out`), which the standing check would otherwise do at its next pass. The standing confirmer runs on every server and does a pass only while an immigration gate admits anyone, so opening one starts it without a restart.

Every other deployment known is a row of `federated_deployment`: added by an administrator or from the terminal, or recorded when first contacted (`origin`), with a note, its pinned key, and when it was first and last contacted. Contacting one (`contact`: `fetch_document`, then `record_contact`) reads its document and pins the key it presents the first time; later the same key is `confirmed`, a new key reached from the pinned one through the document's handovers is pinned in its place (`handedOver`), and any other is refused (`keyChanged`) and kept as `offered_key` until an administrator accepts exactly that key (`accept_key`), after confirming the change with its administrators, since a key that changes unannounced may mean someone else answers at its domain. A deployment not yet known is recorded as first contacted, so whatever contacts strangers must check `admits` first. Forgetting a deployment drops its pin and its list entries. Calls to other deployments (`app::federation::fetch`) are HTTPS only, follow no redirect, time out after ten seconds, read at most 64 KiB, and connect only to public addresses (`app::outbound::PublicResolver`, which filters as it connects, so a name cannot pass a check and then resolve elsewhere; link previews refuse the same addresses through `is_public_address`); `[federation.development]` adds trusted roots and allows private addresses, for `scripts/dev_federation.py`. A failure is `502` `deploymentUnreachable`, whose detail says which.

Holders of Manage federation manage the directory from the dashboard (`/admin/federation`, `/admin/federation/deployments[/{domain}[/contact|/key|/lists/{list}]]`). The terminal does the same (`aspen-chat-server federation …`, where `accept-key` takes the offered key's fingerprint), and alone replaces this deployment's key (`app::federation::keys`). `rotate-key --planned` has the outgoing key sign a handover (a JWS naming the new key), which deployments that pinned any key of the chain follow on their own; `rotate-key --compromised` makes none, since a key that may be in someone else's hands vouches for nothing, and every deployment that pinned the old key then refuses the new one until its administrators accept it. Fingerprints are `SHA256:` and the key's SHA-256 digest in base64, as SSH prints them.

Signing in abroad (`app::federation::abroad`): a signed-in user asks their home for an assertion naming one other deployment (`POST /auth/assertions` with `audience`), which the home signs only when its emigration gate admits that deployment for their kind of account, and records in `user_foreign_deployment` (`GET /users/@me/foreign-deployments`, for their other devices; not shown to moderators). An assertion is a compact JWS with EdDSA (`app::federation::jws`, RFC 7515 and 8037, each kind of statement with its own `typ`): the home, the audience, the user's id at home, two minutes of life, a single-use id, how the sign-in proved who they are (`SignInMethod`, recorded on every `refresh_token`: `password`, `secondFactor`, `passkey`, or a bot's `token`), and their profile. The user hands it to the other deployment (`POST /auth/federated-sign-in`, unauthenticated), which reads only its issuer before verifying, contacts that issuer only if an immigration gate might admit it, verifies against the pinned key (contacting again once when that fails, to follow a handover), checks the audience, lifetime, and the gate for the account's kind, refuses a password-only sign-in where it requires two factors (`strongerSignInRequired`), remembers the id in Valkey until it expires so it is used once, and signs the user in with an ordinary session, owing it no second factor. The first time, it makes their foreign user: a `user` row with `home_domain` and `home_id`, its own id, no password, and a registration invite redeemed when `immigration_invite_required` is set for their kind of account. Usernames are unique among a deployment's own users only (`user_name_key` is partial), password sign-in and the terminal look only at them, and records carry `homeDomain`. The profile is the home's (its name, display name, pronouns, bio, avatar, and the email address its user shows, if any; see Email): each sign-in writes it and announces changes, the user cannot edit it abroad (only their status), and their avatar is copied into the host's storage (`home_icon` names the home's original), fetched from the home itself at `GET /federation/icons/{icon}`, which serves only its own users' avatars. Abroad, a foreign user changes no sign-in security, owns no bots, and signs in nowhere else; sessions last as native ones do. Refusals are `federationRefused` (a closed gate, federation off, or an account that is not the home's), `assertionInvalid`, and `deploymentUnreachable`.

The client (phase three) keeps a session on every deployment the home lists, one sync each, and shows them together: one community rail, ordered by the account preference `rail.order` at home, and one DM list, with another deployment's routes under `/at/{domain}/…`. A user stops using a deployment with `DELETE /users/@me/foreign-deployments/{domain}`, which their other devices follow, and signing out at home signs out everywhere. Browsers call other deployments' APIs directly, so every deployment allows every CORS origin: every request carries a bearer token rather than a cookie, so no origin gains anything by it. `GET /auth/methods` names the deployment's `federationDomain`, which a client needs to offer signing in elsewhere.

How the protocol evolves is `spec/federation.md`, the contract any implementation or fork keeps. In short: within a protocol version only by addition, readers ignoring unknown fields, enum values (an explicit `Unknown` variant, treated as the most cautious known value: an unknown `Gate` admits no one, a key of an unknown `KeyAlgorithm` is never used), and event, statement, and notice types; anything else is a new version served beside the old; every deployment supports the versions of the last thirty-six months. A deployment says what it speaks (`app::federation::protocol`: `Protocol` with `version`, `minimum`, and `capabilities`, and `Software`, which is for people to read and never decides anything) in its document and `GET /auth/methods`. Each peer's is recorded on contact (`federated_deployment.protocol_version`, `protocol_minimum`, `capabilities`, `software_name`, `software_version`) and shown in the dashboard and the terminal; a home whose versions do not meet this deployment's is refused (`federationRefused`), as a client refuses to sign in at one it shares no version with. A feature added after a version is released is a capability: bare names are Aspen's, and a fork names its own by a domain it controls, reversed. Aspen is not yet used outside its developers' machines, so every feature is the baseline of version 1 and Aspen's own capability list is empty; each plugin a deployment runs is named among its capabilities by the plugin's id (`Protocol::with_plugins`; see Plugins). `spec/fixtures/federation/` holds payloads of each version and of an imagined newer deployment, which the tests read, and `scripts/dev_federation.py up --alpha-bin … --beta-bin …` runs two builds against each other.

DMs across deployments (phase four) are DMs on one of them, the host: whoever starts one picks it among the deployments they are on, and a deployment hosts a DM only when starting it with one of its own users in it (`app::dm::open_dm`, `federationRefused` otherwise); it may go on after they leave. Everyone in it therefore has an account on the host, where its rules (a shared community, blocks) apply. When a DM is started with, or gains, users of other deployments, the host tells each one's home with a notice (`app::federation::notices`: a signed `aspen-notice+jwt` of kind `dmJoined`, POSTed to `/api/v1/federation/notices` and tried again a few times in the background). Statements from elsewhere, notices and assertions alike, are verified in one place (`app::federation::received::receive`: the issuer read before anything else, a gate of the right direction, the pinned key, the audience, the lifetime, single use, a common protocol version). The home passes a `dmJoined` on to the user's devices as the `foreignDmJoined` event while the user still uses the sender, and they sign in there if they are not and read the DM. User records carry `homeId` beside `homeDomain`, so a client knows one person across deployments and holds a block made on any of them everywhere.

A foreign user stays welcome only while their home says so (phase five). About every `[federation] standing_interval_seconds` (an hour), one API server, under an advisory lock its transaction holds (so it is let go however the pass ends), asks each home about its users with a session here (`app::federation::standing`: a signed `aspen-standing-request+jwt` POSTed to `/api/v1/federation/standing`, answered with a signed `aspen-standing+jwt`, each request naming at most `MAX_USERS`, 128, so that it and its answer fit within the 16 KiB a statement may be (`jws::MAX_LENGTH`), with an answer's body read no further than that): `good` confirms them (`user.home_confirmed_at`), `gone` retires them, and `refused` (the user left this deployment, or their home's emigration gate closed to it), or a standing not known, ends their sessions (`app::login::revoke_all_sessions`); so does this deployment's own immigration gate closing to the home, and a home unreached for `standing_grace_seconds` (a day). A user who deletes their account has their home send an `accountDeleted` notice to every deployment they used, which retires them there at once. Holders of Ban users ban a foreign user from the deployment as they ban its own (`app::user_ban`; see Administration): their sessions end, signing in abroad refuses them (`federationRefused`) until the ban ends or is lifted, and the dashboard's user directory marks users of other deployments by their domain. A home answers `refused` for a user of its own it has banned, which ends their sessions on every deployment they visit at its next standing check.
