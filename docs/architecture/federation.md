# Federation

A user of one deployment may use others: their home deployment is where the account was made, any other is foreign to them, and they are a foreign user there. Five phases build it: (1) each deployment's identity, key, policy, and directory of other deployments; (2) signing in abroad, with foreign users as local rows naming their home; (3) a client holding sessions on several deployments; (4) DMs across deployments and the notices between them; (5) revocation, deletion notices, and moderating foreign users. All five are built (`app::federation`, `api::federation`, and in the client `Deployments`; see `client/docs/architecture/deployments.md`).

A deployment is its domain (`app::federation::Domain`: a DNS name of two or more labels, lowercase, with `:port` when not 443, never an IP address), the host of its `public_url` when that is `https` (a deployment at an `http` address has none and takes no part), and an Ed25519 key pair (`federation_key`, the current one being the one not retired, made by the first server to start with a domain, with `ring`, which also signs and verifies). The private key is kept in the database so that every API server signs with the same one, which makes the database's backups as sensitive as the key. It publishes its domain, keys, and gates at `GET /.well-known/aspen` (`DeploymentDocument`: the current key first, then those it replaced within `HANDOVER_WINDOW_DAYS`, ninety, sixteen at most, `MAX_DOCUMENT_KEYS`), outside `/api/v1`, unauthenticated, cacheable for five minutes, and `404` without a domain. Federation needs HTTPS: other deployments are reached only at `https://{domain}`.

Policy is gates, which are deployment settings (`FederationPolicy`, read from each server's copy of the settings; see Administration): for users and, separately, bots, `emigration` (this deployment's accounts using others) and `immigration` (others' accounts using this one), each `closed` (the default), `open`, `allowList`, or `blockList`. The modes operators speak of are the users' gates: none, emigration, immigration, and full, each open or with a list. A gate with a list reads one of twelve lists (`FederationList`, named by who, which way, and allow or block: `usersEmigrationAllow` … `botsSharedBlock`); with `shared_list` both directions read the `Shared` list, and must then be the same kind. Every list keeps its entries whether or not a gate reads it, so switching a gate from an allow list to a block list never turns the allowed into the blocked. `admits` decides from the gates and the lists that decide a deployment (`directory::lists_of`): those it is on, and every block list a deployment is on whose host is its host or a parent of it, on any port (`Domain::blocked_by`), so blocking `evil.org` blocks `a.evil.org` and `evil.org:8443` too, while an allow list admits only the deployments it names, exactly. Each directory record carries the result as `admission`, beside the lists it is on itself. Holders of Manage federation change the gates from the dashboard (`PATCH /admin/federation`) and the terminal from `settings set`; every server follows at once, a gate opens only once the deployment has a domain, and a change to an immigration gate or its shared list, a deployment put on a list or taken off one (`directory::set_listed`), or one forgotten (`directory::remove`), from the dashboard or the terminal, signs out at once the users of other deployments the gates no longer admit (`standing::shut_out`), which the standing check would otherwise do at its next pass. The standing confirmer runs on every server and does a pass only while a gate is open, so opening one starts it without a restart.

Every other deployment known is a row of `federated_deployment`: added by an administrator or from the terminal, or recorded when first contacted (`origin`), with a note, its pinned key, and when it was first and last contacted. Contacting one (`contact`: `fetch_document`, then `record_contact`) reads its document and pins the key it presents the first time; later the same key is `confirmed`, a new key reached from the pinned one through the document's handovers is pinned in its place (`handedOver`; `follow_handovers` walks back from the current key through at most the document's first `MAX_DOCUMENT_KEYS` keys, trying first the key each handover's `kid` names, so a document cannot make it verify more than a few hundred signatures), and any other is refused (`keyChanged`) and kept as `offered_key` until an administrator accepts exactly that key (`accept_key`), after confirming the change with its administrators, since a key that changes unannounced may mean someone else answers at its domain. Until then the deployment is suspended: since the key pinned may be one that leaked (`rotate-key --compromised` at its end), `received::receive` refuses everything it signs, even what verifies against the pinned key, `accountDeleted` notices included (`statementKeyPending`), and `record_contact` signs out its users here at once (`standing::shut_out_home`), as each standing pass does again. Every standing pass also reads again the document of each deployment in use (`directory::IN_USE_SQL`: added by an administrator, noted, on a list, the home of a user here, or used by one of this deployment's users) that a gate admits, whose key is pinned and that was last contacted more than `standing_interval_seconds` ago (`standing::refresh_documents`), the longest contacted first and all within two minutes, beside the standing check rather than before it, so a key a deployment replaced stops verifying here within about an interval, whether the replacement was planned (the handover is followed) or not (it is suspended). A deployment not yet known is recorded as first contacted, so whatever contacts strangers must check `admits` first. A statement whose sender has no key pinned, or that does not verify against the pinned one, has its sender contacted (`contact::contact_verifying`) and is checked against the key its document presents before anything is recorded, so a forged statement naming a stranger leaves no row and pins nothing. A deployment recorded on first contact and not in use is forgotten, with its pin, once it has gone uncontacted for thirty days (`directory::prune_unused`, at each standing pass), unless it waits on an administrator to accept a key it offered; a note keeps one. Forgetting a deployment drops its pin and its list entries; one on a block list is refused (`409`) until it is taken off its block lists, since forgetting it would otherwise admit it wherever a gate blocks only those listed. Calls to other deployments (`app::federation::fetch`) are HTTPS only, follow no redirect, time out after ten seconds, read at most 64 KiB, and connect only to public addresses (`app::outbound::PublicResolver`, which filters as it connects, so a name cannot pass a check and then resolve elsewhere, and which no domain passes by being an address, since `Domain::parse` refuses whatever a URL would read as one; link previews refuse the same addresses through `is_public_address`, which counts as public only what lies outside every special-purpose network IANA lists, judging an IPv6 address that carries an IPv4 one, mapped, compatible, NAT64, or 6to4, by the IPv4 address); `[federation.development]` adds trusted roots and allows private addresses, for `scripts/dev_federation.py`. A failure is `502` `deploymentUnreachable`, whose detail says which, for an administrator contacting a deployment. A statement can name any domain as its issuer and so make this server call it, so a sender contacted for a statement (`received::contact_sender`: signing in abroad, notices, standing requests) that cannot be reached is refused with one detail however it failed (`statementSenderUnreachable`), the specific one going to the log; and one sender is contacted that way at most every fifteen seconds, or a minute after it could not be reached, a statement in between being checked against whatever key that contact left pinned.

Holders of Manage federation manage the directory from the dashboard (`/admin/federation`, `/admin/federation/deployments[/{domain}[/contact|/key|/lists/{list}]]`). The terminal does the same (`aspen-chat-server federation …`, where `accept-key` takes the offered key's fingerprint), and alone replaces this deployment's key (`app::federation::keys`). `rotate-key --planned` has the outgoing key sign a handover (a JWS naming the new key), which deployments that pinned any key of the chain follow on their own; `rotate-key --compromised` makes none, since a key that may be in someone else's hands vouches for nothing, and every deployment that pinned the old key then refuses the new one until its administrators accept it. Fingerprints are `SHA256:` and the key's SHA-256 digest in base64, as SSH prints them.

Signing in abroad (`app::federation::abroad`): a signed-in user asks their home for an assertion naming one other deployment (`POST /auth/assertions` with `audience`), which the home signs only when its emigration gate admits that deployment for their kind of account, and records in `user_foreign_deployment` (`GET /users/@me/foreign-deployments`, for their other devices; not shown to moderators). An assertion is a compact JWS with EdDSA (`app::federation::jws`, RFC 7515 and 8037, each kind of statement with its own `typ`): the home, the audience, the user's id at home, two minutes of life, a single-use id, how the sign-in proved who they are (`SignInMethod`, recorded on every `refresh_token`: `password`, `secondFactor`, `passkey`, or a bot's `token`), and their profile. The user hands it to the other deployment (`POST /auth/federated-sign-in`, unauthenticated), which reads only its issuer before verifying, contacts that issuer only if an immigration gate might admit it, verifies against the pinned key (contacting again once when that fails, to follow a handover), checks the audience, lifetime, and the gate for the account's kind, refuses a password-only sign-in where it requires two factors (`strongerSignInRequired`), refuses an assertion that calls a bot a person or a person a bot, whether by its sign-in method or against the foreign user it already made (`statementInconsistent`), since the gate it checks is the one for the kind the assertion claims, remembers the id in Valkey until it expires so it is used once, and signs the user in with an ordinary session, owing it no second factor. The first time, it makes their foreign user: a `user` row with `home_domain` and `home_id`, its own id, no password, and a registration invite redeemed when `immigration_invite_required` is set for their kind of account. At most `[federation] max_arrivals_per_home_per_day` (five hundred) of one home's users and bots arrive for the first time in a UTC day, counted in Valkey across every server (`abroad::count_arrival`), so a home that mints accounts cannot fill this deployment with them; the rest are refused (`federationRefused`) until the next. Usernames are unique among a deployment's own users only (`user_name_key` is partial), password sign-in and the terminal look only at them, and records carry `homeDomain`. The profile is the home's (its name, display name, pronouns, bio, avatar, and the email address its user shows, if any; see Email): each sign-in writes it and announces changes, the user cannot edit it abroad (only their status), and their avatar is copied into the host's storage (`home_icon` names the home's original; a sign-in naming the original already copied copies nothing, and the copy a new one replaces is deleted once nothing uses it, `app::icon::delete_if_unused`, so a home cannot fill the host's storage by changing it), fetched from the home itself at `GET /federation/icons/{icon}`, which serves only its own users' avatars, and only those that are PNG, JPEG, WebP, or GIF (`app::icon::IMAGE_TYPES`, the only kinds an icon may be uploaded as), with `X-Content-Type-Options: nosniff` and `Content-Security-Policy: default-src 'none'; sandbox`, since it answers on the web client's origin; the host takes only those kinds from it. Abroad, a foreign user changes no sign-in security, owns no bots, and signs in nowhere else; sessions last as native ones do. Refusals are `federationRefused` (a closed gate, federation off, or an account that is not the home's), `assertionInvalid`, and `deploymentUnreachable`.

The client (phase three) keeps a session on every deployment the home lists, one sync each, and shows them together: one community rail, ordered by the account preference `rail.order` at home, and one DM list, with another deployment's routes under `/at/{domain}/…`. A user stops using a deployment with `DELETE /users/@me/foreign-deployments/{domain}`, which their other devices follow, and signing out at home signs out everywhere. Browsers call other deployments' APIs directly, so every deployment allows every CORS origin: every request carries a bearer token rather than a cookie, so no origin gains anything by it. `GET /auth/methods` names the deployment's `federationDomain`, which a client needs to offer signing in elsewhere.

How the protocol evolves is `spec/federation.md`, the contract any implementation or fork keeps. In short: within a protocol version only by addition, readers ignoring unknown fields, enum values (an explicit `Unknown` variant, treated as the most cautious known value: an unknown `Gate` admits no one, a key of an unknown `KeyAlgorithm` is never used), and event, statement, and notice types; anything else is a new version served beside the old; every deployment supports the versions of the last thirty-six months. A deployment says what it speaks (`app::federation::protocol`: `Protocol` with `version`, `minimum`, and `capabilities`, and `Software`, which is for people to read and never decides anything) in its document and `GET /auth/methods`. Each peer's is recorded on contact (`federated_deployment.protocol_version`, `protocol_minimum`, `capabilities`, `software_name`, `software_version`) and shown in the dashboard and the terminal; a home whose versions do not meet this deployment's is refused (`federationRefused`), as a client refuses to sign in at one it shares no version with. A feature added after a version is released is a capability: bare names are Aspen's, and a fork names its own by a domain it controls, reversed. Aspen is not yet used outside its developers' machines, so every feature is the baseline of version 1 and Aspen's own capability list is empty; each plugin a deployment runs is named among its capabilities by the plugin's id (`Protocol::with_plugins`; see Plugins). `spec/fixtures/federation/` holds payloads of each version and of an imagined newer deployment, which the tests read, and `scripts/dev_federation.py up --alpha-bin … --beta-bin …` runs two builds against each other.

DMs across deployments (phase four) are DMs on one of them, the host: whoever starts one picks it among the deployments they are on, and a deployment hosts a DM only when starting it with one of its own users in it (`app::dm::open_dm`, `federationRefused` otherwise); it may go on after they leave. Everyone in it therefore has an account on the host, where its rules (a shared community, blocks) apply. When a DM is started with, or gains, users of other deployments, the host tells each one's home with a notice (`app::federation::notices`: a signed `aspen-notice+jwt` of kind `dmJoined`, POSTed to `/api/v1/federation/notices` and tried again a few times in the background). Statements from elsewhere, notices and assertions alike, are verified in one place (`app::federation::received::receive`: the issuer read before anything else, a gate of the right direction, the pinned key, the audience, the lifetime, single use, a common protocol version). The home takes but ignores a `dmJoined` whose `by` it would not accept as a name and display name of its own, and passes any other on to the user's devices as the `foreignDmJoined` event while the user still uses the sender, and they sign in there if they are not and read the DM. User records carry `homeId` beside `homeDomain`, so a client knows one person across deployments and holds a block made on any of them everywhere; it believes them only in records from the viewer's own home, since any other deployment could name anyone as its user's home (see `client/docs/architecture/deployments.md`).

A foreign user stays welcome only while their home says so (phase five). About every `[federation] standing_interval_seconds` (an hour), one API server, under an advisory lock its transaction holds (so it is let go however the pass ends), asks each home about its users with a session here, sixteen homes at a time and each within twenty seconds, holding no pooled connection while it waits on one, and leaving a home that keeps failing alone for a while, the wait doubling up to an interval (its users still lose their sessions at the grace) (`app::federation::standing`: a signed `aspen-standing-request+jwt` POSTed to `/api/v1/federation/standing`, answered with a signed `aspen-standing+jwt`, each request naming at most `MAX_USERS`, 128, so that it and its answer fit within the 16 KiB a statement may be (`jws::MAX_LENGTH`), with an answer's body read no further than that): `good` confirms them (`user.home_confirmed_at`), `gone` retires them, and `refused` (the user left this deployment, or their home's emigration gate closed to it), or a standing not known, ends their sessions (`app::login::revoke_all_sessions`); so does this deployment's own immigration gate closing to the home, and a home unreached for `standing_grace_seconds` (a day). A home answers only for its users who signed in at the asker (`user_foreign_deployment`), saying `gone` of those whose account was deleted, and `refused` of any other id whatever is true of it, so an answer reveals nothing of accounts the asker was never given. A user who deletes their account has their home send an `accountDeleted` notice to every deployment they used, which retires them there at once; since it only takes away, it is taken from any home whose key is pinned, even one no gate admits any more (`received::Senders::AdmittedOrPinned`, which verifies against the pinned key alone and contacts no one), while every other notice is taken only from a deployment a gate admits. Holders of Ban users ban a foreign user from the deployment as they ban its own (`app::user_ban`; see Administration): their sessions end, signing in abroad refuses them (`federationRefused`) until the ban ends or is lifted, and the dashboard's user directory marks users of other deployments by their domain. A home answers `refused` for a user of its own it has banned, which ends their sessions on every deployment they visit at its next standing check.
