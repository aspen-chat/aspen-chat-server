# Voice

Calls run on voice servers, separate processes registered in the `voice_server` table (seeded from `[[voice.servers]]` in `aspen.toml` by name at startup, and managed through `/voice-servers`). The crate `voice_protocol/` is what the API server and the voice servers share: the join token (HMAC-SHA256 under `[voice] token_secret`) and the control messages. A client never authenticates with a voice server directly: `POST /channels/{channel}/voice/join` (Join voice) returns a token naming the user, the channel, the candidate servers, and whether they may speak, share a screen, turn on a camera, and offer files (Speak, Share screen, Use camera, Transfer files, as they stood when it was issued; `voice_protocol::token::Grants`), plus those candidates and the grants. A token admits one connection to each server it names: the voice server remembers the nonces of tokens it has accepted until they expire (`UsedTokens`) and refuses one used again, so someone removed cannot come back on the token they joined with. The voice server refuses a microphone producer without `speak`, a screen or screen audio producer without `share_screen`, and a camera producer without `camera`, by the participant's grants as they now stand. The API server keeps those current (`app::voice::recheck`): every event says which calls it may change access to (`app::events::rechecks_of`, matching every event with no wildcard: a role's permissions, a role given or taken or deleted, an override, a channel moved or deleted, an owner named, a member removed, banned, or leaving, a group DM left, a block, a deployment role, a ban, an account deleted), `publish_event` notes them, and once the request, task, or operator command that published them is done (`app::events::noting` and `settle`) the participants of those calls are rechecked, and whenever a join's report is applied it rechecks the joiner, so a token issued before a change is brought in line. A participant who may no longer view the channel or join voice there, or who is banned from the deployment or gone, is removed (`VoiceCommand::Kick` with reason `accessLost`, which their client tells them of); everyone else is sent their grants (`VoiceCommand::Grant`), and the voice server, when they changed, closes the producers they may no longer send, withdraws their offers if they may no longer offer files, and tells their client (`grantsChanged`), which stops what it may no longer send and opens the microphone it may now send. A channel already in a call is offered only that call's server; otherwise every enabled server with room that has reported within `offer_silence_seconds` (a server that has never reported has not started) is a candidate, at most `candidate_limit` (ten) of them chosen at random for now. The client measures its own latency to each candidate and tries them nearest first; a server that fails to start the session is reported with `POST /voice-servers/{server}/failures`, which counts distinct users within `failure_window_seconds` and disables the server at `failure_threshold` (five) until an operator enables it again.

Voice servers publish `VoiceReport`s to the JetStream stream `aspen_voice_reports` (`voice_protocol::control`). Reports are spread over `REPORT_PARTITIONS` (64) lanes by the channel they are about (the last byte of its id, which is random in a UUIDv7, modulo 64; a report about the whole server, its load, goes by the server's id), and speaking changes, which come many times faster than anything else, go in 64 lanes of their own, so each report's subject (`VoiceReport::subject`) is `aspen.voice.report.{lane}.{server}` or `aspen.voice.speaking.{lane}.{server}`. Every report about a call therefore names its channel. The API servers create the stream (in memory, kept until applied: work-queue retention, a day at most) and read it in `app::voice::reports`: every lane has one durable consumer, shared by all the API servers, that hands out one report at a time and the next only once that one is acknowledged, and every API server reads every lane, applying at most half as many reports at once as its pool has database connections, so requests always have the other half. So the reports about one channel are applied once, in the order they were sent, by whichever API server takes each, its calls one after another included (a channel's call always ends before its next one starts), while the 128 lanes are applied side by side: a busy channel holds up only its lane, and speaking changes never hold up joins and leaves. A speaking change writes nothing, so it is passed on as a `voiceSpeaking` event to the channel it names without a transaction or a lookup. Removing a voice server clears its waiting reports. A report is acknowledged once it has been applied; one that fails because the database or NATS is unreachable is tried again a second later, up to three times, holding back its lane's later reports meanwhile, and any other failure drops it. A report whose acknowledgement was lost is delivered again, so applying one twice changes nothing more. On the voice server, reports go out through one queue (`Reporter`) in the order they are made. Some reports can still be lost: those sent while NATS is unreachable, those the stream loses when NATS restarts, and those dropped. So every `SNAPSHOT_INTERVAL_SECONDS` (a minute), and whenever it reconnects to NATS, a voice server also sends a snapshot: a `sessionSnapshot` for every call it holds (its session, channel, and each participant's mute, deafen, and sharing state), then a `sessionsHeld` for every lane, empty ones included, listing its calls in that lane's channels, made and queued together so no other report comes between them and each describes things as of its place in the order; each part goes in its own lane, after every report about those calls sent before it. The API server makes the record match: it records a missing session or participant as their own reports would, corrects states, removes participants not listed, and ends with reason `serverLost` any session recorded on that server in that lane that `sessionsHeld` leaves out (the database computes the lane of each session's channel the same way), logging a warning for each repair, since one means a report was lost. A server's first snapshot waits a full interval after it starts, so the calls it held before a restart are carried on by their people rejoining (below) rather than ended first. A room keeps its place until its end is reported, and leaves it in the same step, so a snapshot lists a closing room until then and never after. `load` records when the stream took it rather than when it was applied, so a report that waited in the stream does not make a dead server look alive. Each API server counts the reports it applies (`aspen_voice_reports_applied_total`) and how long each waited from reaching the stream to being applied (`aspen_voice_report_wait_duration_seconds`), by type, which shows the record of calls falling behind. `app::voice::sessions::apply_report` turns each report into rows and client events inside one transaction: `voiceSession` create and delete, `voiceParticipant` create, update, and delete, and the custom `voiceSpeaking` event. A session exists from the first participant's report until the last one leaves. Voice servers also report their load every fifteen seconds. A server silent for `offer_silence_seconds` (a minute) is not offered to new joiners, a call bound to such a server is skipped when someone joins its channel (they get fresh candidates), and the reaper ends every session on a server silent for `session_silence_seconds` (a day), so a dead voice server never leaves phantom calls while a brief outage of the report link does not end anyone's call. The reaper also ends any call that has gone `idle_session_seconds` (a day) without ever holding two people at once, so a forgotten client cannot hold a voice server slot. A voice server reports a session only once it holds the room, so the session it reports is the channel's call from then on: any session already recorded for that channel, whether the same server's room lost to a restart or another server's that the joiner could not reach, is ended with reason `serverLost`, which sends its participants to rejoin, and their offers now name the reporting server. Every ending publishes a `voiceSessionEnded` event with a reason (`empty`, `serverLost`, `idle`, `serverRemoved`) just before the session's `delete`; a client that was in an idle-ended call shows its user a dialog saying the call was ended to free server resources. Nested `[voice]` keys can be set from the environment with a double underscore, `ASPEN_VOICE__IDLE_SESSION_SECONDS=30` for instance, which is how tests shorten the limits. Community reads sideload calls with `include=voice`, as the DM list does. A call is held in a voice channel, a DM, or a group DM (see Threads and DMs); any other channel is refused with `voiceChannelOnly`. Commands from the API server to a voice server (mute, kick) travel on `aspen.voice.command.{server}`. `PATCH /channels/{channel}/voice/participants/{user}` with `{"muted": bool}` server-mutes someone and `DELETE` on the same path removes them from the call; both answer `202 Accepted`, because the voice server applies the command and its report is what changes the participant record, so the caller watches for the `voiceParticipant` event rather than reading the response as the result. Both take Manage calls; a DM's call has no moderators.

## The voice server

`voice_server/` is the media process: a mediasoup SFU (each participant uploads once and the server forwards to everyone else) with an HTTP server for the health check clients measure latency against (`GET /health`, CORS open) and the signalling socket (`GET /ws`). It reads `voice_server.toml` from the working directory (gitignored; `id` is the server's row in the registry, `token_secret` is the API server's, plus NATS, `listen_addr`, `workers`, `[rtc]` with the media interface `ip`, `announced_address`, and the port range, and `[transfer]` for file transfers' STUN and TURN; see File transfers), with `ASPEN_VOICE_SERVER_` environment variables overriding it, using `__` for nesting. The announced address is what goes into ICE candidates: set it for a server behind NAT; left unset with `ip` bound to every interface (the default), the host's primary interface address is announced, which suits a development machine. It must never be a loopback address, and the server refuses to start with one: Firefox does not pair its own host candidates with a loopback peer, so signalling would succeed and media would never flow. Every client is limited (`voice_server/src/limits.rs`, built-in values in `voice_server/src/limits.toml`, laid under the `[rate_limits]` of `voice_server.toml` the way the API server's are). `GET /health` and opening `GET /ws` are limited per address, honouring `trusted_proxies`, and refused with `429` and `Retry-After`. An address may hold `max_pending_sockets_per_ip` (eight) sockets that have not identified, and no message may exceed `max_message_bytes` (256 KiB). Each signalling frame type, and every frame together as `any`, is limited per `user`, `ip`, `channel` (the call), or `global`; a refused frame is dropped with a non-fatal `error` saying how long to wait, in its text and as `retryAfterSeconds` (a refused `identify` is a fatal one, the same way). The limits let someone moving from call to call join a dozen times back to back, and every two seconds or so after that, as the API server's limit on join offers does. The counters are in process, since every client of a call talks to this one server. Independently of rate, a participant holds at most one producer per source (microphone, screen, screen audio), so no client can multiply what everyone else in the call receives. The limit format, the GCRA arithmetic, and the trusted-proxy address rule are shared with the API server through the `limits/` crate (`aspen_limits`). Run it with `cargo run -p voice_server`; `cargo run -p voice_server -- --gen-signal-schema` writes `voice_signal_schema.json` (gitignored), the JSON Schema of every signalling frame, for the client's code generator. `voice_server estimate-capacity` (`voice_server/src/capacity.rs`) gives the `capacity` to register the server with: it reads the hardware (cores and any cgroup CPU quota, memory and any cgroup limit, the default route's link speed) and the media settings (`workers`, each at most one core, and the RTC port range), measures on this CPU what a forwarded Opus and H.264 stream and a participant in whole calls cost, with a mediasoup worker on loopback for a few seconds, and reports the smallest of the CPU, memory, bandwidth, and port limits after a safety margin, for a call shape given by flags (`--call-size`, `--screen-share`, `--audio-kbps`, `--screen-kbps`, `--margin`, `--link-mbps`, `--json`). mediasoup recognises an H.264 keyframe by its sequence parameter set, and a video consumer forwards nothing until it has seen one, so anything that sends synthetic H.264 (the calibration, the bench's simulated screens) leads each keyframe with an SPS and a PPS, as an encoder does.

Signalling is `voice_protocol::signal`: `identify` with the join token, then `ready` with the router's RTP capabilities and who is in the call; the client loads a mediasoup device, sends `setCapabilities`, creates and connects a send and a receive transport, and produces its microphone. The server creates a paused consumer on the client's receive transport for every producer of everyone else, present and future, announced with `newConsumer` and resumed by the client's `resumeConsumer`. A client can also ask for a producer it feeds itself with `produceRtp`: the server creates a plain RTP transport (SRTP, RTP and RTCP multiplexed, the sender's address learned from its first packet), answers `rtpProduced` with the address, SSRC, payload type, and key, and makes the client a consumer of its own producer as a preview. `consumeRtp` is the other direction: it makes the client's receive transport a plain one, answered with `rtpConsuming` (address and key), so every consumer the client is given sends to it over SRTP; the benchmark's simulated participants use both, producing `microphone` and `screen` without a browser. The desktop shell's game capture sends H.264 this way, straight from its helper to the voice server, so the router advertises H.264 constrained baseline alongside VP8 and Opus, listed after VP8: a browser producing video takes the router's first codec it can send, and Chromium's H.264 encoder is the software OpenH264, which drops frames on screen content. The game's audio, where the platform can capture it, is a second such producer (source `screenAudio`, Opus, declared `sprop-stereo` because consumers inherit the producer's codec parameters and a browser decodes Opus as mono without it), one plain transport per producer, and only the video is previewed back to its sender. On Linux the picture is an ordinary browser screen producer and only the game's sound arrives this way, beside it. A camera is a producer of its own (`camera`, video from the same send transport), which consumers tell apart from a screen by its source. Mute pauses the microphone producer on the server and deafen pauses every audio consumer (a shared screen stays visible to a deafened participant), both reported to the API server. A screen share is a second producer from the same send transport, `screen` for the picture and `screenAudio` for any sound the browser captured with it; mute never touches either. Every transport assumes a participant can take 10 Mbps before it has measured (`INITIAL_OUTGOING_BITRATE`, mediasoup's default being 600 kbps), so a share reaches its viewers sharp from its first seconds and each receiver's own bandwidth estimate brings it down where it must. The `participantState` report carries `sharing_screen`, sent when a screen producer starts or closes as well as with mute and deafen changes, and `VoiceParticipant.sharingScreen` follows it so a client can mark who is sharing without being in the call. Speaking comes from mediasoup's audio level observer (300 ms interval, -50 dBvo). A call is a room: one router on one worker, created with the first participant and closed with the last, each step reported. Two joins that start a channel's call at once share the room the first of them made. A user who joins again from another socket replaces their participant, and a socket leaving takes out only the participant it made, so the replaced socket closing never takes out its successor. A room closes the moment its last participant leaves: whoever arrives while it is still being torn down waits until its end is reported and then starts the channel's next call, so the API server never hears of the new session before the old one's end, and nobody is let into a room that is about to go. `voice_protocol/examples/fake_voice_server.rs` sends any report or command by hand, which is how the API server's side is tested without media.

Screen sharing is a second producer from the client, and the desktop shell can also share a game captured with libobs; both are described in `client/docs/architecture/screen-sharing-and-game-capture.md`. The client (`VoiceCall` in `client/packages/protocol/src/voice.ts`) pings every candidate's `/health`, tries them nearest first, and reports a server that fails to start its session. A client whose call ended with reason `serverLost` or `serverRemoved` rejoins the channel on its own after a random delay of at most one second, so the participants of a lost call do not all hit the API server in the same instant; `idle` and `empty` endings are not rejoined.
