# Plugins

Plugins are WebAssembly components the operator installs (`app::plugin`, `api::plugin`,
`operator::plugins`), built against `spec/plugin.wit` and described by a manifest
(`app::plugin::manifest`, whose schema is `spec/plugin_manifest.schema.json`); `spec/plugins.md`
is the design and `docs/operators/plugins.md` the operator's guide. `plugins/word_filter` is an
example plugin, built for `wasm32-wasip2` in a workspace of its own, which exercises every hook
and most host calls.

**Installing.** Only the terminal installs (`app::plugin::install::install`): it checks the manifest (`Manifest::check`: a reversed-domain id, semver, interface version 1, every message key the manifest names present in its default language, settings fields well formed, permissions and what they need going together), compiles the component against the host's linker to prove it imports nothing the host lacks (`Plugins::check_component`), shows what it asks for, and writes the row of `plugin` (manifest, component, granted permissions, `mode`, `position`, settings), off. `dms` is granted only with `--grant-dms`. A manifest with a `principal` makes its account (a `user` row with `bot` set, no owner, and `plugin` naming it, which `app::bot::delete` refuses to delete) and publishes its commands as any bot's are. An upgrade replaces manifest and component, keeps mode, order, whether it is on, and the settings it still has, and asks again when it asks for more. `remove` turns it off, drops the component and its annotations (clients draw none for a plugin `GET /plugins` does not list, so these go without events), and takes its principal out of every community; `purge` deletes its storage, its communities' rows, and its settings, keeping the row (the record that it was installed) and its principal, which installing it again takes up. Settings, mode, order, and on/off are also the dashboard's under the deployment permission Manage plugins (`/admin/plugins`, `/admin/plugin-order`). Every change touches `updated_at` and is announced on the core NATS subject `aspen.plugins.changed` (`registry::announce`), on which every API server reloads (`Plugins::reload`), compiling a component again only when its SHA-256 changed.

**Running.** `app::plugin::registry::Plugins` holds the plugins that are on, compiled (`PluginPre`), in order, and caches each community's rows of `community_plugin` for at most a minute, forgotten at once when a community's use changes (the same subject, naming the community). `running_in_community` is every `everywhere` plugin and every `optIn` plugin the community turned on, each with the community's settings (defaults filled in); `running_in_dms` is those granted `dms`; a thread runs where its parent does. Each call is a fresh instance in a store of its own (`host::Instance`): memory capped at `[plugins] memory_mib`, and a deadline kept by the engine's epoch, which a thread of its own ticks every millisecond; at each tick a call within its deadline yields to Tokio and one past it traps, and the whole call, host calls included, is cut off at the deadline (`host::within`). WASI is linked with nothing behind it (no preopens, sockets, environment, or arguments). Host calls live on `host::Call`, apart from the store's WASI state, since what they hold across an await must be shareable between threads.

**Intercepting.** `app::message::create_message` and `update_message` call `intercept::wanted` and, when any plugin running there intercepts the hook, check the author's permission to post first and then `intercept::decide`, before the saving transaction opens. Each plugin sees the text the one before left; a rewrite needs `messages.rewrite`, may not exceed the longer of the text and 4000 characters, and may not tag anyone or anything the text did not (`tags_within`, by `mention::parse`); a refusal needs `messages.refuse` and becomes `pluginRefused` with the plugin's reason in the request's language. A call that fails counts as allowing or refusing (`pluginUnavailable`) as its manifest's `failure` says; a rewrite or refusal without its permission counts as a failure. Commands, warnings, and the system account's notices are not intercepted, nor a principal's own messages by its own plugin. The plugins that rewrote a message are stored in `message.altered_by` and carried as `alteredBy`, an edit replacing them (its `Update` event carries the new set). Actions a plugin asks for while intercepting (`host::Deferred`) run once the hook has answered (`principal::run_deferred`).

**Observing.** Each plugin that observes anything has a durable JetStream consumer of its own (`observe::run`, named from its id), which every API server pulls from with explicit acknowledgement: an event its call fails on is delivered again a second later, three times at most, and only while the stream retains it (`MAX_EVENT_AGE`). A DM's events come once per recipient's subject; `first_copy` keeps, in Valkey, which subject's copy the plugin handles, so it is told once and a redelivery of that copy is still handled (events on a community's subjects come once, and need no such note). Message events are told with the message as saved (read after its transaction commits, retrying briefly), only where the plugin runs and with `messages.read`; `botCommandInvoked` reaches the plugin whose principal it names as `command-invoked`; a `communityPlugin` event of its own reaches it as `plugin-enabled` or `plugin-disabled`.

**What the host answers, and as whom.** `host::Call` checks the granted permission of every call. Reads are made as the caller of a route (`Phase::Route`) and otherwise as the plugin's principal, never as the plugin itself: `read-message` goes through `channel_access` for that reader, and is refused where the plugin does not run (`running_at`). Attachments are readable when they belong to what the call was shown, or, in a route, to a message the caller may read, and only up to `attachmentLimit`. `fetch` reaches only the manifest's hosts, over HTTPS, through a client that resolves public addresses only and follows no redirects, never while intercepting, with bodies of at most 4 MiB. Storage (`storage`) is keyed by plugin, scope, and key in `plugin_storage`; a scope must be where the plugin runs, and in a route where the caller may look (a channel they may view, a community they belong to, themselves). `plugin.storage_bytes` counts keys and values against `storageQuota`, changed only when a value's length does. `forget` deletes a scope's values (a channel's with its threads', a community's with its channels') from `delete_channel`, `delete_community`, and `user::retire`. Counters (`counter-add`) are Valkey keys per plugin, window, and key, expiring with their window. Actions (`act`) run as the principal through `app::message`, `app::react`, `app::role::remove_member`, and `app::ban::ban_member`, inside `noting` and `settle` as a request's would, and are refused while the principal is banned from the deployment.

**Annotations and events.** `messageAnnotation` records are published with `EventScope::Message` (the message's channel, and its `Aspen-Channel`) and sideloaded with `include=annotations` as `included.messageAnnotations`, read only for messages the read already allowed. `userAnnotation` records are published with `EventScope::UserEverywhere`, as a profile is, and read with `GET /users/{user}/annotations`. One of each kind per plugin and subject; setting one again is an `update`. `pluginEvent` carries the plugin's kind and JSON payload (16 KiB at most) to a channel's viewers, a community, or one user, and `expected_kind` routes it by which of `channel` and `community` it names. A `communityPlugin` event (a community turning a plugin on or off, or configuring it) carries `Aspen-Requires: managePlugins`, so only the community's managers receive its settings.

**Routes.** `/api/v1/plugins/{plugin}/routes/{*path}` (`api::plugin::route`) is outside the OpenAPI document and rate limited by `api::rate_limit::PLUGIN_ROUTE` (`plugin_routes` in `rate_limits.toml`, per user per plugin and per plugin). A body is at most 64 KiB and an answer 1 MiB. An answer is served on the API's origin, so a content type a browser would render as a document or run as script becomes `application/octet-stream`, and every answer carries `Content-Security-Policy: default-src 'none'; sandbox` and `X-Content-Type-Options: nosniff`.

**Catalogue and federation.** `GET /plugins` lists the plugins that are on, each with its name, description, community settings fields, the permissions its principal asks for, whether it runs in DMs, and its messages in the reader's language (a pseudo-locale made from its default language), from which clients draw annotations, `alteredBy`, and settings forms. The deployment's document and `GET /auth/methods` name each plugin that is on as a capability (`Protocol::with_plugins`).

**When access is given or taken away.**

1. *Who can observe it, and by which routes?* A message's annotations: whoever may read the message, through its channel's events and message reads' sideloads. A person's annotations: whoever shares a community with them, through their profile's events and `GET /users/{user}/annotations`. A community's use of a plugin: holders of Manage plugins, through `communityPlugin` events and `GET /communities/{community}/plugins`. A plugin's events: whoever its audience names, as any event of that scope. What a plugin keeps: through its routes, as the caller may look. The catalogue: every signed-in user.
2. *What decides it, and where is that checked?* `channel_access` in `host::Call::readable_message`, `scope`, `annotate_message`, and `read_attachment`; `require_member` for community scopes; the event feed's model for annotation, plugin, and `communityPlugin` events (by `Aspen-Channel` and `Aspen-Requires`); `Permissions::MANAGE_PLUGINS` in `app::plugin::community`; where the plugin runs in `Plugins::runs_at`.
3. *When the deciding permission is lost, what happens to what is already open?* Losing View channel (an override, a role, a move, a removal, a ban) stops the channel's annotation and plugin events reaching that stream from that point, as for messages; reads and routes check at each call. Losing Manage plugins stops `communityPlugin` events at once (the model's `Aspen-Requires`). A community turning a plugin off, or the operator turning it off or removing it, stops its hooks on every server within moments (the cache is forgotten on the announcement), and its routes answer `notFound` once it is off; a community turning it off, or the operator removing it, also takes its principal out, whose role goes with it. A principal removed from a community, or stripped of its role's permissions, is refused its next action by the same checks a member's would be; one banned from the deployment is refused every action. Revoking `dms` (reinstalling without `--grant-dms`) stops its hooks in DMs. The client drops annotations of plugins `GET /plugins` no longer lists.
4. *When it is gained, how does a client already open find out?* A reader who gains View channel reads the channel's messages, and their annotations with them, as any channel gained. A member gaining Manage plugins reads `GET /communities/{community}/plugins` when they open the community's plugin settings. A plugin turned on appears in `GET /plugins`, which the client reads again when it meets a plugin it does not know.
5. *Does every path that changes it announce it?* Community changes publish `communityPlugin` events inside their transaction; the principal's joining and leaving publish its membership and role events; annotation changes publish their own events; the operator's and the dashboard's changes announce on `aspen.plugins.changed`. Removing a plugin deletes its annotations without events, and every client infers that from the catalogue.
6. *Is it published inside the transaction that makes the change?* Annotation, `communityPlugin`, membership, and role events are, so a rollback is answered by `communityResync` as for any request.

`scripts/check_permissions.py` checks that a plugin's annotations and events stop reaching someone who loses View channel, that its route stops answering them for the channel's storage, that a community's plugin settings reach only holders of Manage plugins, and that turning the plugin off takes its principal out.
