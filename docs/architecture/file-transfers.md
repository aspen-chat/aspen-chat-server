# File transfers

While in a call, a participant holding Transfer files (`transferFiles`, which the join token carries as `transfer_files`, and the API server sends again whenever it changes; losing it withdraws their standing offers, see Voice) may offer a file to everyone else in it, for as long as they choose (sixty seconds by default, from `MIN_VALID_SECONDS` to `MAX_VALID_SECONDS`, an hour, so an unattended offer stays a thing for the people in a call rather than a device seeding a file to whoever joins; any number of people may accept one). Each participant who accepts starts one transfer between the two of them, over a WebRTC data channel of their own, encrypted end to end; the bytes never touch mediasoup, storage, or the API server. The sender chooses when offering whether receivers may connect directly, and each receiver must choose how their transfer travels among the ways the sender and the server allow, even when there is only one: `directPreferred` (hole-punched, which could expose each side's address to the other, falling back to the relay when the server relays) or `relayOnly` (through the voice server's TURN relay, so neither learns the other's address). The dialogs say so in those words, and name the relay's limit. A transfer outlives its offer, so one under way finishes after the offer runs out; either side may cancel one at any time, which ends it at once on both sides and at the relay; nothing resumes. The sender's client answers acceptances by itself, so an offer works while its sender is away.

The voice server keeps the offers and transfers of each call (`voice_server/src/rooms/transfers.rs`) and passes each transfer's peer connection signalling between its two sides (`voice_protocol::signal`: `offerFile`, `withdrawFile`, `acceptFile`, `transferSignal`, `endTransfer`, and back `fileOffered`, `fileWithdrawn`, `transferStarting`, `transferSignal`, `transferEnded`). Everyone in the call is told when a transfer starts and ends and between whom (`transferLinkChanged`, and `links` in `ready`), never what it carries, and the client draws each as a dashed line in the accent colour marching from sender to receiver between their tiles, turning only at right angles (`TransferLinks`). Each transfer's row shows the mode the receiver preferred and the route actually in use, read from the peer connection's selected candidate pair (`routeOf`). The network side is `voice_server/src/transfer.rs`: one UDP port (`[transfer] port`, 3478) answering STUN, so no third party learns who is connecting, and TURN (the `turn` crate), whose credentials name one side of one transfer (by the offer's `record`, the id the server made for it, never the client's), work only while that transfer is live, and only from `ADDRESSES_PER_CREDENTIAL` (two) client addresses, so one side holds at most two allocations and no credential can take the relay's ports, and whose allocations are deleted the moment it ends. The relay forwards only between its own live allocations (`LivePorts`, so never to a port of its range on the machine that no allocation holds; every relayed transfer is relayed at both ends), its ports may not overlap the media range or the STUN port (the server refuses to start otherwise), looped back inside the server so it needs no hairpin NAT, and every relayed transfer on the server shares `[transfer] relay_mbps` (50; 0 turns relaying off): a pacer sends from one queue at that rate, dropping the odd datagram with rising probability past half full and whatever overflows `QUEUE_SECONDS` of it, so a data channel's congestion control settles near the limit rather than stalling on a run of losses. The client side is `FileTransfers` (`client/packages/protocol/src/transfers.ts`), which `VoiceCall` feeds its frames, and `FilesPanel`, `FileDialogs`, and `TransferLinks` in the app. Where the receiver can choose a place first, accepting opens a picker and the file is written there as it arrives (a `FileSink`), closed only when every byte is in and discarded when the transfer ends otherwise: in a browser with the File System Access API (Chromium, so the desktop app too), and in the mobile apps through their `AspenFilesPlugin` (`client/packages/app/src/api/filesBridge.ts`): Android's system create-document picker names the file, and on iOS, which has no picker for a file yet to be written, the user chooses a folder and the file is made there under the name it was sent with. Elsewhere (Firefox and Safari) a file is held until it has all arrived and then saved.

The deployment keeps a record of every offer and transfer for its moderators (`app::file_transfer`, tables `file_offer` and `file_transfer`): who offered what, by name and size, who received it, in which mode, and how it ended, never the file. The voice server reports each offer (`VoiceReport::FileOffered`) and each transfer's start and end into the report stream (see Voice), naming the offer by an id of its own (`record`, UUIDv7) rather than the id the client chose, so no client can make its offer collide with another in the record; a transfer's start is recorded once however many times its report arrives. A snapshot carries only calls, so a transfer report that is lost is missing from the record for good. It tells who sent what to whom in private calls, so holders of Moderate any community read it, at `GET /admin/file-transfers` (newest offer first, paged by `before` and `limit`, one person's by `filter[user]`, as sender or receiver) and in the dashboard's File transfers section. The deployment setting `file_transfers` (see Administration) off turns the whole feature off: no join token then grants Transfer files, and turning it off or on rechecks every call (`Recheck::Everyone`), so the participants' grants follow at once.
