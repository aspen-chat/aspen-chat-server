# Event routing

Every event is published on a NATS subject that names whose it is (`app::events`): `aspen.events.c.{community}.ch.{channel}` for what happens in a channel (messages, reactions, polls, calls), `aspen.events.c.{community}.all` for the community itself and what is defined in it (channels, categories, invites, memberships), and `aspen.events.u.{user}` for what is the user's alone (preferences, and their own membership changes). A DM or group DM belongs to no community, so both what happens in it and the DM itself are published to each recipient's user subject (a recipient who just left gets the update that removes them too); a thread belongs wherever its parent does. Where a channel belongs is its `ChannelHome`, which never changes and is cached for the process's life. Each API server reads the stream once (`app::event_feed`): one ordered JetStream consumer over every event subject, and one dispatcher task that hands each event in order to `event_feed_shards` routing tasks (one per logical CPU by default); each connection belongs to one shard, which delivers to it the events whose subject's owner (`events::subject_owner`) is its user or one of their communities. NATS does work in proportion to events times API servers, however many people are connected, and the per-reader cost of fanning an event out to a big community is spread across cores. What a connection receives is its user's subject plus each community they belong to, computed from the database when it connects, never from the client. Their own `userCommunity` events change it as the dispatcher routes them, in stream order, so a join brings the community's events from that point and a leave ends them. A channel's events, and a community channel's own events (its creation, moves, deletion, and overrides), carry an `Aspen-Channel` header naming the channel whose View channel permission decides who gets them (a thread's parent). The dispatcher holds an `app::visibility::CommunityModel` of each community a local connection reads (owner, role permissions, each channel's category, the overrides), loaded with the first connection that needs it, applies the events that change it in stream order, and attaches the model as it then stands to each of the community's events; a shard decides each reader's view from that model and the roles the reader holds, which it follows from their own `userCommunity` events. An event that changes who may view the channel it names (an override set or cleared, a move, a creation, a deletion) also carries the model as it stood before (`FeedEvent::before`), and reaches whoever may view the channel by either: those losing it learn they have, those gaining it learn they may look it up, and nobody else learns the channel exists. A category's own events and its overrides' carry an `Aspen-Category` header instead, and reach those whose roles its own overrides leave View channel there (`CommunityModel::can_view_category`), an override's change also those who could view it before (`FeedEvent::before`), and its deletion (`ModelChange::CategoryDeleted`, which drops its overrides from the model) only those who could view it before; a category the model holds no overrides of is decided by the community's permissions alone (see Roles and permissions). A channel the model does not know, one not yet made or deleted, nobody views; so a new channel's overrides, published ahead of it, reach only those they let view it. A model adopted for a community whose events were retained before the dispatcher held it attaches to each of those the model as it stood there, so a catch-up judges them by the permissions of their moment. A permission name the model does not know (from a newer server) is passed over rather than costing the whole change. An event may also need a community permission besides membership, named in the `Aspen-Requires` header, with `Aspen-Creator` naming one member who receives it anyway: every invite event, which carries the invite's code, needs Manage invites, and reaches whoever made the invite; a community's use of a plugin (`communityPlugin`), whose settings may be its moderators' alone, needs Manage plugins; the shard checks it against the same attached model. A plugin's `pluginEvent` names a channel, a community, or neither, and `expected_kind` routes it as an event of that scope (see Plugins). A membership event's copy for the community (`events::for_community`) leaves out the member's own list position, `sortIndex`, which only they receive, and a reorder reaches only them; reads likewise give `sortIndex` for the caller's own membership alone. A connection that joins a community no local connection reads is dropped and resumes, loading the model as it registers again. Every request runs inside `app::events::noting`, through `app::events::settle_after` (a layer around every API route, `settle_after_request`, which handles each request in a task of its own that runs to its end even when its client goes away, so abandoning a request between its publishing and its commit rolls nothing back; work dropped part way all the same, by a panic, is settled as having failed), as do the background tasks and operator commands that change access, which notes the communities and users each event was published to, with the transaction it was published in (`pg_current_xact_id`, when inside one and not in a savepoint within it), and the calls it may change access to (`app::events::rechecks_of`); `app::events::settle` then rechecks those calls (see Voice), and an access-changing event published outside one is logged as an error. Events are published before their transaction commits, so one rolled back after publishing leaves events the database does not bear out: work that fails after publishing announces a resync for what it published outside a transaction, or in one the database says did not commit (`pg_xact_status`, read once the work is done, a transaction it cannot answer for counting as not committed), while a failure after the publishing transaction committed announces nothing, what it published being true. For communities that is `communityResync` for each, on which every dispatcher drops the community's model and the connections reading it resume with it loaded afresh, and clients read the community again; and work that fails after publishing to users' own subjects (a DM, a membership, a setting) announces `userResync` to each, on which every dispatcher drops the user's connections, which register afresh with their communities and roles read from the database, and their clients read everything they hold again, as they do when a resume is refused. Each connection knows the sign-in it belongs to (`app::login::sign_in_id`, half the SHA-256 of its refresh token); signing out, revoking other sign-ins (a password or second factor change), revoking all of them (a ban, an account deleted, a home's standing withdrawn), or rotating a bot's token publishes `signInsEnded` to the user's subject, which reaches only the streams of the sign-ins it names and closes them with 4401 after it, as an account ban (`accountBanned`) closes all of theirs with 4410. Their session was checked against the database when they identified, possibly before such an end committed, so a registration whose `resumeAfter` lies at or past a retained one that concerns it is refused with the same code rather than resuming beyond it (`Retained::catch_up`), and one before it is replayed the end and closes after it. A stream also closes with 4401 when its sign-in's refresh token expires, at the moment it was read to expire when the stream identified (a bot's token does not expire). Operator commands that change what someone may do (`admin`, `communities set-owner`) publish through `app::events::Publisher`, the same publishing without a server context. REST list reads leave out hidden channels with `app::visibility::Visibility`, the same resolver. The dispatcher also holds what the stream retains (the last `MAX_EVENT_AGE`, indexed by owner, loaded from the stream at startup) and serves every catch-up from it: `resumeAfter`, and a first connection's replay window, applying membership changes it passes over. A connection is registered inside the dispatcher's loop, its catch-up queued and then its registration sent down its shard's ordered channel ahead of the next event, so it sees each event once, and a reconnect storm costs NATS nothing. Each user may hold `[limits] max_event_streams_per_user` streams (20) on one API server and each client address `max_event_streams_per_address` (200, counted from the upgrade, before `identify`), counted in the process (`app::event_feed::StreamCaps`) so that a server that stops leaves no count behind; one more is closed with 4429 (`tooManyStreams`, `tooManyStreamsFromAddress`). Each connection's queue holds `event_queue_size` events; one that fills is dropped and its client resumes. If the feed's sequence jumps (NATS lost events, or the in-memory stream was recreated), every local connection is dropped and learns from `resumed: false` to rebuild. Sequence numbers are the stream's and stay global and monotonic, so `resumeAfter` works unchanged with gaps in it.

`publish_event(state, conn, scope, event)` takes an `EventScope` naming the ids the caller has (a channel, a message, a session, a community, a membership, a user) and resolves the rest on the caller's connection, so an event published inside a transaction can name rows that transaction wrote. `expected_kind` pairs every event variant with the kind of scope it must be published with in a match with no wildcard arm: an entity added without deciding its routing does not compile, and a scope of the wrong kind is refused at run time. An event about a user (their profile) is published once to every community they belong to and once to themselves; every copy carries the same `Aspen-Event-Id` header, surfaced as `eventId` on the frame, and the client drops repeats. The copies are bounded by `[limits] max_communities_per_user` (500 by default), enforced where memberships are made.

Presence is pulled, not pushed (`app::user_status`). A user is `online` while they have a connection and have used Aspen recently, `away` while connected but idle, and `offline` once no connection is left. Two Valkey keys say so: `user:{uuid}:online`, set when they connect the event stream (or make any authenticated request) and refreshed by its pings, whose setting when it was not set is their coming online and writes `user.last_seen_at`, and `user:{uuid}:active`, set by each `activity` frame a client sends on its event stream while its user interacts with it (at most once a minute; the stream ignores closer ones) and expiring after `[presence] away_after_seconds` (ten minutes). Both keys belong to the user rather than a connection, so any active device keeps them online and any connected one keeps them from going offline. A bot is never away: whatever marks it connected sets its `active` key too, for as long, since it uses Aspen through the API rather than as a person does. Nothing announces a change. Clients ask `GET /users/statuses?ids=…` (at most 100 ids) for the users they show, which the reference client does every thirty seconds while the page is visible. Someone's presence is told only to themself and to those who share a community or a DM with them, or own them as a bot, and never to anyone they have blocked (`app::user_status::presence_visible`, through `statuses_for`): to everyone else it answers `offline`, so presence does not tell a stranger, or someone blocked, when a person is about. Every record that carries `onlineStatus` (`GET /users/{user}`, the `users` sideloaded with messages, reactors, DMs, blocks, and report cases, members, bots) fills it the same way for the caller, and the member sample orders those who blocked the caller as if they were not connected.

How many people are online in a channel is counted on the server (`app::channel_presence`, `GET /channels/{channel}/presence`), since no client knows every member of a large community. It counts those whose status is online, not away, among the community's members who may view the channel (`app::visibility::viewers`), or among a DM's recipients; a thread counts as its parent. Reading every member's keys would cost as much as the community is large, so each community has a Valkey sorted set, `community:{uuid}:online`, of members who may be online, each scored with the Unix time their listing runs out (`app::user_status`). Setting either of someone's keys lists them in each of their communities for the longer of the two keys' lifetimes and half as long again, and `user:{uuid}:listed`, living that half, keeps the fan-out to one write per community per half lifetime however often they are active or connected; joining a community lists the joiner there at once. So the set holds everyone connected, away or not. A count reads the listings that have not run out (dropping those that have), confirms each by its presence keys, and keeps those who may view the channel, so it costs as much as the number connected. Every viewer sees the same count, so each server keeps a channel's for ten seconds (`app::recent`), and requests that arrive while one is being worked out wait for it rather than starting their own. Nobody is counted for someone who may not learn their presence (`presence_visible`): a DM's count keeps only those the caller may, and a community channel's shared count has the caller's blockers who are online and may view it now taken off, so for the up to ten seconds the shared count lags a blocker coming online or leaving, the blocked caller's count is one off. The member sample (see Roles and permissions) reads the same set, keeping those whose keys say they are online or away, and each server keeps a community's for ten seconds the same way. The reference client asks for the open channel's count with each presence poll.
