# Event routing

Every event is published on a NATS subject that names whose it is (`app::events`): `aspen.events.c.{community}.ch.{channel}` for what happens in a channel (messages, reactions, polls, calls), `aspen.events.c.{community}.all` for the community itself and what is defined in it (channels, categories, invites, memberships), and `aspen.events.u.{user}` for what is the user's alone (preferences, and their own membership changes). A DM or group DM belongs to no community, so both what happens in it and the DM itself are published to each recipient's user subject (a recipient who just left gets the update that removes them too); a thread belongs wherever its parent does. Where a channel belongs is its `ChannelHome`, which never changes and is cached for the process's life. Each API server reads the stream once (`app::event_feed`): one ordered JetStream consumer over every event subject, and one dispatcher task that hands each event in order to `event_feed_shards` routing tasks (one per logical CPU by default); each connection belongs to one shard, which delivers to it the events whose subject's owner (`events::subject_owner`) is its user or one of their communities. NATS does work in proportion to events times API servers, however many people are connected, and the per-reader cost of fanning an event out to a big community is spread across cores. What a connection receives is its user's subject plus each community they belong to, computed from the database when it connects, never from the client. Their own `userCommunity` events change it as the dispatcher routes them, in stream order, so a join brings the community's events from that point and a leave ends them. A channel's events, and a community channel's own events, carry an `Aspen-Channel` header naming the channel whose View channel permission decides who gets them (a thread's parent). The dispatcher holds an `app::visibility::CommunityModel` of each community a local connection reads (owner, role permissions, each channel's category, the overrides), loaded with the first connection that needs it, applies the events that change it in stream order, and attaches the model as it then stands to each of the community's events; a shard decides each reader's view from that model and the roles the reader holds, which it follows from their own `userCommunity` events. An event may also need a community permission besides membership, named in the `Aspen-Requires` header, with `Aspen-Creator` naming one member who receives it anyway: every invite event, which carries the invite's code, needs Manage invites, and reaches whoever made the invite; the shard checks it against the same attached model. A membership event's copy for the community (`events::for_community`) leaves out the member's own list position, `sortIndex`, which only they receive, and a reorder reaches only them; reads likewise give `sortIndex` for the caller's own membership alone. A connection that joins a community no local connection reads is dropped and resumes, loading the model as it registers again. REST list reads leave out hidden channels with `app::visibility::Visibility`, the same resolver. The dispatcher also holds what the stream retains (the last `MAX_EVENT_AGE`, indexed by owner, loaded from the stream at startup) and serves every catch-up from it: `resumeAfter`, and a first connection's replay window, applying membership changes it passes over. A connection is registered inside the dispatcher's loop, its catch-up queued and then its registration sent down its shard's ordered channel ahead of the next event, so it sees each event once, and a reconnect storm costs NATS nothing. Each connection's queue holds `event_queue_size` events; one that fills is dropped and its client resumes. If the feed's sequence jumps (NATS lost events, or the in-memory stream was recreated), every local connection is dropped and learns from `resumed: false` to rebuild. Sequence numbers are the stream's and stay global and monotonic, so `resumeAfter` works unchanged with gaps in it.

`publish_event(state, conn, scope, event)` takes an `EventScope` naming the ids the caller has (a channel, a message, a session, a community, a membership, a user) and resolves the rest on the caller's connection, so an event published inside a transaction can name rows that transaction wrote. `expected_kind` pairs every event variant with the kind of scope it must be published with in a match with no wildcard arm: an entity added without deciding its routing does not compile, and a scope of the wrong kind is refused at run time. An event about a user (their profile) is published once to every community they belong to and once to themselves; every copy carries the same `Aspen-Event-Id` header, surfaced as `eventId` on the frame, and the client drops repeats. The copies are bounded by `[limits] max_communities_per_user` (500 by default), enforced where memberships are made.

Presence is pulled, not pushed (`app::user_status`). A user is `online` while they have a connection and have used Aspen recently, `away` while connected but idle, and `offline` once no connection is left. Two Valkey keys say so: `user:{uuid}:online`, set when they connect the event stream (or make any authenticated request) and refreshed by its pings, and `user:{uuid}:active`, set by each `activity` frame a client sends on its event stream while its user interacts with it (at most once a minute; the stream ignores closer ones) and expiring after `[presence] away_after_seconds` (ten minutes). Both keys belong to the user rather than a connection, so any active device keeps them online and any connected one keeps them from going offline. A bot is never away: whatever marks it connected sets its `active` key too, for as long, since it uses Aspen through the API rather than as a person does. Nothing announces a change. Clients ask `GET /users/statuses?ids=…` (at most 100 ids) for the users they show, which the reference client does every thirty seconds while the page is visible.

How many people are online in a channel is counted on the server (`app::channel_presence`, `GET /channels/{channel}/presence`), since no client knows every member of a large community. It counts those whose status is online, not away, among the community's members who may view the channel (`app::visibility::viewers`), or among a DM's recipients; a thread counts as its parent. Reading every member's keys would cost as much as the community is large, so each community has a Valkey sorted set, `community:{uuid}:online`, of members who may be online, each scored with the Unix time their listing runs out (`app::user_status`). Setting someone's `active` key lists them in each of their communities to run out half the key's lifetime after the key can, and `user:{uuid}:listed`, living that half, keeps the fan-out to one write per community per half lifetime however often they are active; joining a community lists the joiner there at once. A count reads the listings that have not run out (dropping those that have), confirms each by its presence keys, and keeps those who may view the channel, so it costs as much as the number online. Every viewer sees the same count, so each server keeps a channel's for ten seconds, and requests that arrive while one is being worked out wait for it rather than starting their own. The reference client asks for the open channel's count with each presence poll.
