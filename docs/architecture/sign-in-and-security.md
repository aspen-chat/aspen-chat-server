# Sign-in and security

Usernames are unique regardless of case (`user_name_key` indexes `lower(name)`), so a password sign-in finds its account however the name is capitalized (`app::user::named`, which the operator commands that take a username use too), and the per-username sign-in rate limit counts every capitalization of a name as one. A password sign-in (`POST /auth/login`) answers `{"status": "signedIn", …tokens}` or, for an account with two-factor sign-in on, `{"status": "secondFactorRequired", "ticket", "methods"}`; the ticket (Valkey, five minutes) is finished with `POST /auth/login/second-factor` and an authenticator code or a recovery code, or with a passkey. An account has two-factor sign-in on while it holds a second factor, a confirmed authenticator app (`totp_secret`, RFC 6238, SHA-1, six digits, thirty seconds, one step of drift, each step accepted once) or a passkey (`passkey`), and it then holds ten single-use recovery codes (`recovery_code`, SHA-256 digests only). Adding the first factor makes the codes and signs out every other session, as changing the password does; signing out, or being signed out so, also closes that sign-in's open event streams (`signInsEnded`; see Event routing) and stops its phone being woken; removing the last drops the codes, unless `[auth] require_two_factor` is set, in which case it is refused with `lastSecondFactor`. Wrong codes and passwords given to prove who someone is count per user in Valkey, and ten within fifteen minutes lock that user's second factors for the rest of the window (`tooManyAttempts`). All of this is `app::two_factor`. Hashing and checking passwords (Argon2, 19 MiB and most of a core for a noticeable time each) run on at most `[auth] password_hashing_threads` blocking threads at once (`app::login::password_work`); a request that waits `password_hashing_wait_seconds` without one is refused with `503` `serverBusy` and `Retry-After`, so a burst of sign-ins costs a bounded amount of memory, leaves the rest of the server its CPU, and sheds what it cannot serve soon rather than slowing everyone down.

A sign-in records when it last proved who its user is (`refresh_token.verified_at`). Changes to security settings (adding or removing a factor, new recovery codes, deleting the account, and changing the password of an account with two-factor sign-in on) need that to be within `[auth] reverify_seconds`, or they answer `reauthenticationRequired`; `POST /auth/reauthenticate` refreshes it with the password, or, when two-factor sign-in is on, with a code, and a passkey `reauthenticate` ceremony does the same. The settings themselves are `/users/{user}/security`, `/users/{user}/totp` (with `/confirmation`), `/users/{user}/passkeys/{passkey}`, and `/users/{user}/recovery-codes`, the user themself only. With `require_two_factor` set, a session of an account without a second factor can reach only those, `reauthenticate`, passkey ceremonies, and `logout`; everything else, the event stream included (close code 4403), answers `twoFactorEnrollmentRequired`.

Passkeys are WebAuthn through `webauthn-rs` (`app::passkey`). A passkey signs its user in on its own and also serves as the second factor after a password; registration requires a discoverable credential so that sign-in needs no username. Every exchange with an authenticator is a ceremony: `POST /auth/passkey-ceremonies` with a purpose (`signIn`, `register`, `reauthenticate`) returns the options for `navigator.credentials`, the verifier's state waits in Valkey for five minutes, and `POST /auth/passkey-ceremonies/{id}/credential` completes it once, whether or not it verifies. A browser offers a passkey only to pages under `rp_id`, which the desktop and mobile apps are not, so they hand the ceremony to the page this server serves at `/auth/passkey` (outside `/api/v1`; `api::passkey_page`) in the system browser: the ceremony is started with a `handoff` naming a return address (a loopback port, the `aspen:` scheme, or an allowed web origin) and a PKCE `S256` challenge, the page completes it and sends the browser back, and the app claims the outcome with `POST …/claim` and its verifier. The ceremony id travels in the page's URL fragment, so it reaches no server log.

A device signs in another by a QR code through a device link (`app::device_link`, `/auth/device-links`). One side is signed in (the giver) and the other not (the receiver); a computer (the desktop app or a browser) always shows the code and a phone always scans it. A computer that is not signed in starts a `request` (`POST /auth/device-links` without a session, naming itself and giving a PKCE `S256` challenge) and a signed-in phone scans it (`POST …/{link}/scan` with its session); a signed-in computer starts an `offer` and a phone that is not signed in scans it, naming itself and giving the challenge (a signed-in phone is refused, before the code is used, since claiming would replace its sign-in). The link's id is the code's secret, kept in Valkey under a digest like the passkey ceremonies; it lasts a minute unscanned, and one scan takes it (`SET NX` on a scan key, so of two devices scanning at once one wins and the other gets `deviceLinkUsed`, which tells someone whose screen was photographed). The giver then confirms the receiver by the name it gave, with a tap (`PUT …/approval`; the giver of an offer asks `GET …/{link}` every couple of seconds to learn it was scanned), and the receiver claims its sign-in with the verifier (`POST …/claim`, every couple of seconds: the progress, then the sign-in, once). Only the receiver can claim, so a giver approving a stranger's request, or a stranger holding a photographed code, gets no session. Nothing about the devices is looked up: a device's name is what it calls itself ("Firefox on Linux"), and no address or place is recorded. The new sign-in (`login::issue_linked_session`) records the giver's `method` and `verified_at`, so it is no stronger than the giver's, satisfies `require_two_factor` exactly when the giver's did, and makes no security change without verifying again once the giver's verification is stale. Bots and users of other deployments cannot give a sign-in (their sign-ins are their token's and their home's), nor can a session still owing a second factor.

Who can observe a link: only whoever holds its id, which travels in the QR code's URL fragment and the request paths; the giver's own reads are refused to anyone else (`deviceLinkExpired`, as for an unknown link). What decides it is the giver's sign-in: the link records its `sign_in_id`, and the claim issues nothing unless a live, unexpired refresh token of the giver, of an undeleted account, still has that id, and `issue_session`'s ban check passes. So signing out, being signed out by a password change or a first second factor, deletion, and a ban from the deployment, all between the tap and the claim, stop it; after the claim the new sign-in is an ordinary one, ended by all the same things. Nothing is announced: a link has no event, and both sides poll it for its minute. `scripts/check_permissions.py` checks the sign-out and password-change cases.
