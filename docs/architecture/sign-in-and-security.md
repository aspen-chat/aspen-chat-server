# Sign-in and security

A username (`app::user::validate_username`) is 1 to 32 characters of any script, digits, emoji, and punctuation, but no `@` (which sets a tag apart), whitespace (the line and paragraph separators among it), control characters (Cc), or format characters (Cf: zero-width spaces and joiners, direction marks and isolates, the soft hyphen, tags), by which two names that look alike could differ, and it must be in NFC, so one name has one spelling; the client composes a new name to NFC before sending it. Names taken before these rules stand, and sign in as they are; a rename follows them, as do bots' names and the names foreign users' homes give. Usernames are unique regardless of case (`user_name_key` indexes `lower(name)`), so a password sign-in finds its account however the name is capitalized (`app::user::named`, which the operator commands that take a username use too), and the per-username sign-in rate limits count every capitalization of a name as one. There are two (`api::rate_limit::limit_sign_in`): `username` counts every attempt at a name from one client network (an IPv4 /24, an IPv6 /48; `aspen_limits::ClientAddresses::network_key`) before the password is checked, so one network's guesses cannot lock the owner out from anywhere else, and `username_failures` counts the name's wrong passwords from every network together, looked at (`RateLimiter::peek`, which counts nothing) before the password is checked and counted (`note_wrong_password`) only after a wrong one, so the owner's right passwords never spend it. While it is spent password sign-in for the name is refused; passkeys, device links, and a reset by email still reach the account. An unknown name counts like a known one, so the limits tell nothing of which names exist. A password sign-in (`POST /auth/login`) answers `{"status": "signedIn", …tokens}` or, for an account with two-factor sign-in on, `{"status": "secondFactorRequired", "ticket", "methods"}`; the ticket (Valkey, five minutes) is finished with `POST /auth/login/second-factor` and an authenticator code or a recovery code, or with a passkey. An account has two-factor sign-in on while it holds a second factor, a confirmed authenticator app (`totp_secret`, RFC 6238, SHA-1, six digits, thirty seconds, one step of drift, each step accepted once) or a passkey (`passkey`), and it then holds ten single-use recovery codes (`recovery_code`, SHA-256 digests only). Adding the first factor makes the codes and signs out every other sign-in (`login::revoke_other_sign_ins`), as changing the password signs out every other session, and as `DELETE /users/{user}/sign-ins` (signing out everywhere else, `login::end_other_sign_ins`, which needs a recently verified session and publishes `signInsEnded` inside its transaction) does on its own; changing or resetting the password and signing out everywhere else also end every plugin capability URL of the account in the same transaction (see Plugins); signing out, or being signed out so, also closes that sign-in's open event streams (`signInsEnded`; see Event routing), takes it out of any call it joined (its join token names the sign-in; see Voice), and stops its phone being woken; removing the last drops the codes, unless the deployment setting `require_two_factor` is on (see Administration), in which case it is refused with `lastSecondFactor`. Wrong authenticator codes and passwords given to prove who someone is (to finish a sign-in, to re-verify, or as the old password when changing it) count per user in Valkey: ten within fifteen minutes refuse them for the rest of the window, and twenty within a day for the rest of the day, however the quarter hours fall, so the codes cannot be guessed slowly either (`tooManyAttempts`). Each attempt is counted, in one script with each window's expiry, before it is checked; a right one clears the quarter hour's count and is not counted in the day's, which keeps its wrong ones, so attempts sent all at once are checked no more than ten times (`two_factor::limited`). When a wrong one reaches the day's limit, the account's verified address is told, once (`signInLocked`). Since the count is per user, someone who knows the password can keep it reached and lock the owner's authenticator codes and password re-verification for a day; recovery codes (50 random bits, one of ten, beyond guessing at any pace the endpoints allow) are checked outside the limits for that reason, as are passkeys, and a password reset by email does not use them, so the owner always has a way in that the lock does not close. The account's verified address is mailed whenever a second factor is added (`secondFactorAdded`) or removed (`secondFactorRemoved`), or the password is changed (`passwordChanged`) or reset (see Email), queued in the transaction that made the change (`email::outbox::notify`): nothing is queued where the deployment sends no mail or the account has no verified address. All of this is `app::two_factor`. Hashing and checking passwords (Argon2, 19 MiB and most of a core for a noticeable time each) run on at most `[auth] password_hashing_threads` blocking threads at once (`app::login::password_work`); a request that waits `password_hashing_wait_seconds` without one is refused with `503` `serverBusy` and `Retry-After`, so a burst of sign-ins costs a bounded amount of memory, leaves the rest of the server its CPU, and sheds what it cannot serve soon rather than slowing everyone down. No database connection is held while waiting for that work or doing it: each caller reads the hash, gives its connection back, and takes one again afterwards, so a flood of sign-ins cannot hold the pool idle and refuse every other request (`database_pool_wait_seconds`). A sign-in naming no account, or a bot, is checked against a fixed hash no password matches (`login::UNMATCHABLE_PASSWORD_HASH`), so it takes as long as a wrong password and does not tell which names exist. A new password, at registration, changed, or reset, is at least 8 and at most 1024 bytes (`login::check_new_password`); otherwise it is refused with `passwordRequirementsNotMet` naming the `requirement`, `length` or `maxLength`, and a `detail` giving the limit. A sign-in's refresh token (`POST /auth/token-refresh`, `login::try_token_refresh`) gives no session token once its account is deleted or banned from the deployment: it answers `invalidToken`, as an ended sign-in's does, so the app signs out, and signing in again tells of a ban. Refresh and session tokens are 256 random bits kept only as their SHA-256 in hex (`login::token_digest`), as bot tokens are, and a presented token is looked up by its digest, so a copy of the database signs no one in; a sign-in's id (`login::sign_in_id`) is the first half of its refresh token's digest. A refresh token is not rotated when used: it stands for its sign-in until it expires (a year) or the sign-in ends.

An account may also hold an email address, which a deployment can require verified before the account is used, held like a session owing a second factor (close code 4428), and through which a forgotten password is reset; both are described in Email.

A sign-in records when it last proved who its user is (`refresh_token.verified_at`). Changes to security settings (adding or removing a factor, new recovery codes, deleting the account, and changing the password of an account with two-factor sign-in on) need that to be within `[auth] reverify_seconds`, or they answer `reauthenticationRequired`; `POST /auth/reauthenticate` refreshes it with the password, or, when two-factor sign-in is on, with a code, and a passkey `reauthenticate` ceremony does the same. The settings themselves are `/users/{user}/security`, `/users/{user}/totp` (with `/confirmation`), `/users/{user}/passkeys/{passkey}`, and `/users/{user}/recovery-codes`, the user themself only. With `require_two_factor` on, a session of an account without a second factor can reach only those, `reauthenticate`, passkey ceremonies, and `logout`; everything else, the event stream included (close code 4403), answers `twoFactorEnrollmentRequired`. Turned on while such a session's event stream is open, the stream closes with 4403, and the client, told so by the close (`EventStream`'s `onEnrollmentRequired`) or by a refused request, shows the enrollment screen. Authenticator apps and passkey prompts call the deployment by its display name, or "Aspen" (see Administration); an authenticator keeps the name it was given when it was added.

Passkeys are WebAuthn through `webauthn-rs` (`app::passkey`). A passkey signs its user in on its own and also serves as the second factor after a password; registration requires a discoverable credential so that sign-in needs no username, and an account holds at most 50 (`passkey::MAX_PASSKEYS`), checked as a `register` ceremony starts and again, with the account's row held, as it completes. Every exchange with an authenticator is a ceremony: `POST /auth/passkey-ceremonies` with a purpose (`signIn`, `register`, `reauthenticate`) returns the options for `navigator.credentials`, the verifier's state waits in Valkey for five minutes, and `POST /auth/passkey-ceremonies/{id}/credential` completes it once, whether or not it verifies. A browser offers a passkey only to pages under `rp_id`, which the desktop and mobile apps are not, so they hand the ceremony to the page this server serves at `/auth/passkey` (outside `/api/v1`; `api::passkey_page`) in the system browser: the ceremony is started with a `handoff` naming a return address (a loopback port or the `aspen:` scheme; no web page, since the web client runs ceremonies in its own page and a page that forwarded its query would hand the return code on) and a PKCE `S256` challenge, the page completes it, which only checks the credential, and sends the browser back with a one-time return `code` added to the address, and the app claims the outcome with `POST …/claim`, its verifier, and that code; only the claim gives the ceremony its effect (a session issued, a passkey added, a sign-in marked verified). The ceremony id travels in the page's URL fragment, so it reaches no server log. The page's link is a real link on the deployment's own origin, so whoever starts a ceremony can send it to someone else, and the verifier alone would let them claim what that person's passkey approved: a session in their account for a `signIn`, or a verification of a stolen session for a `reauthenticate`. The return code closes that: every return address the server accepts leads back to the device whose browser ran the page (its own loopback or its own app), so the code never reaches someone who sent the link elsewhere, and a ceremony is claimed only where it was run. The page also tells whoever opens it to continue only for a request they made in the app on that device. A `register` or `reauthenticate` ceremony acts on the sign-in that started it (`login::sign_in_id`), so only that sign-in completes it in its own page or claims it after a handoff (`forbidden` otherwise), and the handoff page runs only handed-off ceremonies. A ceremony in Valkey keeps that id, never the sign-in's tokens, and a `signIn` that is a password sign-in's second factor keeps the ticket's key (`login::TicketKey`, holding its digest), never the ticket, and re-verifying marks the sign-in by it, refusing one that has ended. The claim needs the return code: an app that sends none is told to update.

A device signs in another by a QR code through a device link (`app::device_link`, `/auth/device-links`). One side is signed in (the giver) and the other not (the receiver); a computer (the desktop app or a browser) always shows the code and a phone always scans it. A computer that is not signed in starts a `request` (`POST /auth/device-links` without a session, naming itself and giving a PKCE `S256` challenge) and a signed-in phone scans it (`POST …/{link}/scan` with its session); a signed-in computer starts an `offer` and a phone that is not signed in scans it, naming itself and giving the challenge (a signed-in phone is refused, before the code is used, since claiming would replace its sign-in). The link's id is the code's secret, kept in Valkey under a digest like the passkey ceremonies; it lasts a minute unscanned, and one scan takes it (`SET NX` on a scan key, so of two devices scanning at once one wins and the other gets `deviceLinkUsed`, which tells someone whose screen was photographed). Cancelling (`DELETE …/{link}`) removes the link, and a scan or approval under way at that moment finds it gone rather than writing it back (`SET XX`), so a cancelled code stays cancelled. The giver then confirms the receiver by the name it gave, with a tap (`PUT …/approval`; the giver of an offer asks `GET …/{link}` every couple of seconds to learn it was scanned), and the receiver claims its sign-in with the verifier (`POST …/claim`, every couple of seconds: the progress, then the sign-in, once). Only the receiver can claim, so a giver approving a stranger's request, or a stranger holding a photographed code, gets no session. Nothing about the devices is looked up: a device's name is what it calls itself ("Firefox on Linux"), and no address or place is recorded. The new sign-in (`login::issue_linked_session`) records the giver's `method` and `verified_at`, so it is no stronger than the giver's, satisfies `require_two_factor` exactly when the giver's did, and makes no security change without verifying again once the giver's verification is stale. Bots and users of other deployments cannot give a sign-in (their sign-ins are their token's and their home's), nor can a session still owing a second factor. Giving one, by starting an offer or scanning a request, takes a sign-in verified within `[auth] reverify_seconds` (`reauthenticationRequired`, checked before the code is used), since it is a security change: without it a stolen session could mint a sign-in of its own on another device, outliving the stolen one. Starting a link, like starting a passkey ceremony, is limited per address and also, generously, by everyone's starts together (`rate_limits.toml`), since each keeps state in Valkey until it expires.

Who can observe a link: only whoever holds its id, which travels in the QR code's URL fragment and the request paths; the giver's own reads are refused to anyone else (`deviceLinkExpired`, as for an unknown link). What decides it is the giver's sign-in: the link records its `sign_in_id`, and the claim issues nothing unless a live, unexpired refresh token of the giver, of an undeleted account, still has that id, and `issue_session`'s ban check passes. So signing out, being signed out by a password change or a first second factor, deletion, and a ban from the deployment, all between the tap and the claim, stop it; after the claim the new sign-in is an ordinary one, ended by all the same things. Nothing is announced: a link has no event, and both sides poll it for its minute. `scripts/check_permissions.py` checks the sign-out and password-change cases, and that a giver whose verification is stale is asked to verify again.
