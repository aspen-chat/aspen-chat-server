# Custom emoji

A community keeps its own emoji (`app::custom_emoji`, `api::custom_emoji`, table `custom_emoji`): a name and a picture, which is an icon uploaded first through the icon flow (`POST /icons` and its confirmation) as a PNG, JPEG, WebP, or GIF of at most 256 KiB and 128 by 128, which the client scales a still picture down to and refuses a larger GIF for. Each is identified by its community and its own UUIDv7, and the UI calls it by its name alone: 2 to 32 characters of any script, no whitespace or colons, unique within the community ignoring case (`customEmojiNameTaken`). `GET` and `POST /communities/{community}/emoji` list and add them, `PATCH /emoji/{emoji}` renames one, and `DELETE /emoji/{emoji}` removes it with its picture; the last three take Manage custom emoji, which the Moderator and Admin templates hold (the migration gave it to every role holding Manage messages) and the everyone role does not. A community holds at most `[communities] custom_emoji_limit` (1000). Community reads sideload them with `include=emoji`, as `included.customEmoji`, and each change is an event on the community's subject. A message's text names one as `<:id>`, by the id alone, so a rename changes no message and a reader resolves it from the community's list, rendering an unknown id as a marked placeholder; the message box shows `:name:` and encodes it as it sends. A reaction's emoji may be that same reference (`app::react::stored_key`), stored with `react.custom_emoji` naming the emoji, which the server allows only where the message's channel belongs to the emoji's community (a DM has none, `customEmojiNotHere`; another community's, `customEmojiUnknown`); deleting an emoji takes its reactions with it by cascade, which clients apply on the emoji's deletion event. The server never parses `<:id>` in text: an id from elsewhere resolves to nothing where it is read, which is all the rule needs.
