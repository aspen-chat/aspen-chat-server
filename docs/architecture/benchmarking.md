# Benchmarking

`bench/` (`aspen-bench`, with `bench/README.md` as the operator guide) says whether a deployment is up to a job described by a profile: population, load, behaviours, timed events, and service levels. The built-in profiles are `bench/profiles/`. A run is plan, seed, run, purge:

- `aspen-bench plan <profile> --run <tag>` writes an `aspen_bench_protocol::SeedPlan`. The crate `bench_protocol/` holds what `aspen-bench` and the API server share: the plan, the manifest seeding writes, and the coordinator-agent messages.
- `aspen-chat-server bench seed` writes the population straight into the database (`app::benchmark::seed`, batched, history backdated with UUIDv7 ids) and records every user and community it made against the run in `benchmark_run`, `benchmark_user`, and `benchmark_community`. Benchmark users are ordinary users named `bench-<run>-<n>` with one shared password.
- `aspen-bench run` plays the users over the real API and event stream, the way the client does, as open-model Poisson actions with latency measured from when each action was due. A coordinator can spread users over agents on other machines (`aspen-bench agent`), synchronising clocks by Cristian's algorithm so delivery latency is measured across machines. Calls use real SRTP through `produceRtp` and `consumeRtp`, measuring loss, RFC 3550 jitter, and round-trip time. It samples the `[target] metrics` endpoints and names what ran short in the report (`report.json`, `report.html`); `--mode capacity` raises the load step by step until a service level breaks. It exits 0 on a pass, 1 on a fail, 2 on an error; `aspen-bench compare` and `bench/scripts/regression.sh` fail on a slower p99, for CI.
- `aspen-chat-server bench purge --run <tag>` deletes the run's users and communities and every row that came to depend on them, however the run went: it reads the foreign key graph from `pg_constraint`, marks the doomed rows in temporary tables, clears the nullable references among them that close a cycle (any other is left to the order of deletion, since clearing it could break a check on its table), deletes children first in one transaction, and removes stored media after it commits. A table added with a foreign key to anything a benchmark user can make is covered without changes, but a new stored-media column must be added to the purge's list of objects.

Rate limits would stop hundreds of users sharing an address, so an operator can suspend them: `aspen-chat-server limits suspend --for 2h [--scope networks --network CIDR…|--scope all] --reason …`, with `resume` and `status`. The suspension is one record in the NATS KV bucket `aspen_rate_limits` (`aspen_limits::suspension`), watched by every API and voice server. `networks` exempts those networks from the limits that count by address (the voice server's pending socket cap included) and keeps every other limit; `all` lifts them all. It always ends by itself: at its `until`, and never later than each server's own `max_suspension_seconds` after it began, so a forgotten suspension, or one written with a far `until`, cannot leave a deployment open. Servers log a warning every minute while one is in force. It is deliberately a command run with the deployment's credentials and never an HTTP endpoint, so no account, however privileged, can lift the limits that protect a deployment from its own users. A profile with `[limits] suspend = true` suspends for its run and resumes afterwards if the record is still its own.

Both servers export Prometheus metrics (`metrics/`, `aspen_metrics`, whose constants name every series) on a loopback listener: requests by route and status with latency, database pool connections, event publish latency, event streams, deliveries, and the event feed's retained window, routing time, and dropped streams, rate limit checks and refusals, voice reports applied and how long each waited between reaching the report stream and being applied, by type, and process CPU and memory from the API server; rooms, participants, producers, consumers, transports, signalling frames, refusals, and mediasoup worker CPU from the voice server (`[metrics]` in `voice_server.toml`, `127.0.0.1:9465`); and from both, jemalloc's own figures (`aspen_memory_allocated_bytes`, `_active_`, `_resident_`, `_mapped_`, `_retained_`), which tell a leak (allocated keeps rising) from memory the allocator keeps (resident well above allocated). The bench reports heap growth beside resident growth for that reason. A new metric gets its name as a constant there.
